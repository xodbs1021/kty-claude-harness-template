## Context

종결 규약(ADR-0020 후속 이력 2026-09-02 · 2026-09-04)은 코드 검수 게이트를
"무지적 3라운드 + 축 체크리스트"로 닫으라고 한다. 그런데 **그 3라운드를 무엇을
단위로 세는지는 어디에도 없었다.** 한 PR 을 여러 커밋으로 나눠 개발하면 읽는
방법이 둘로 갈린다.

같은 프로젝트(pokeclip-mono)의 두 PR 이 실제로 다르게 읽었다.

*   앞 PR(커밋 7개)은 커밋마다 1라운드를 돌려 그 라운드를 무지적 계수에 넣고,
    PR 전체 차분으로 종결 라운드를 한 번 돌았다. 약 30시간에 닫혔다.
*   다음 PR(커밋 9개 예정)은 커밋마다 무지적 3회를 채웠고, 커밋이 끝날 때마다
    계획서를 코드에 맞춰 고친 뒤 그 계획서를 다시 듀얼 리뷰했다. 착수 뒤 약
    88시간이 지나도록 커밋 넷까지만 닫혔다.

기록 시각으로 어림하면 88시간 가운데 결정 대기가 약 28시간, 일한 시간이 약
60시간이다. 일한 시간 가운데 코드 개발·검수가 27시간, 계획 라운드가 20시간이었다.
계획서는 6,000줄을 넘겼다.

kty 가 물었다 — "왤케 오래걸려? 뭐땜에 병목이생기는거야?", "설계문제야?".
원인을 듣고 정했다 — "그러니까 계획서 동기를 커밋마다 하는게 ㅈㄴ 쓸데없는
짓이라 이거지?", "나도 전체적인 계획 짜놓고 리뷰 받은 다음에 마지막 pr 할 때
리뷰 ㅈㄴ 돌리는게 맞는것같은데?". 그리고 지시했다 — "응 하네스 자체를 이렇게
바꿔 하네스 템플릿에도 이렇게 바꿔놓고".

## Decision

한 PR 을 여러 커밋으로 나눠 개발할 때 종결 규약을 **커밋마다** 되풀이하지
않는다. 리뷰를 몰아서 돌리는 자리는 둘이다 — 개발 전의 계획 게이트(Phase 2)와
PR 직전의 종결 라운드(Phase 3 의 끝).

1.  **계획서는 개발 도중 커밋마다 코드에 맞춰 고치지 않는다.** 계획은 Phase 2
    에서 한 번 리뷰받고 닫는다. 편차는 진행 기록과 통합 장부에 적고, 계획서와
    운영 문서는 종결 라운드 전에 한 번 코드에 맞춘다. 커밋별 작업 지시를 쓰거나
    고치는 일도 계획 게이트를 다시 열지 않는다. `[구조]` 부류 편차만 사용자에게
    회부한다.
2.  **커밋별 검수는 듀얼 1라운드다.** cc·cx 동시 1라운드(보안 트리거면 보안
    검수 병렬)를 돌고 CRITICAL/HIGH 만 고친다. 고친 것이 있으면 수정분 확인
    패스(cc·cx 동시)를 돈다. 확인 패스에도 CRITICAL/HIGH 가 남으면 고치고 한
    번 더 확인하며, 두 번째에도 남으면 사용자에게 회부한다. MEDIUM/LOW 는
    이연해 PR 단계에서 처분한다. 통과한 커밋은 기능 브랜치에 쌓고 커밋마다
    push 한다.
3.  **종결 = PR 전체를 입력으로 한 라운드에서 무지적 3회 ∧ 축 체크리스트 전부
    커버.** 입력은 셋이다 — 기준 브랜치를 동기화한 뒤의 PR 전체 차분, 현재
    계획서, 차분에 들지 않은 운영 문서의 목록. 이연 목록과 착수 체크리스트
    전체를 종결 라운드 프롬프트에 넣는다. 라운드 상한 5회는 종결 라운드에만
    센다. 커밋별 라운드는 상한에도 무지적 계수에도 넣지 않는다.

딸린 규칙은 다섯이다.

*   Phase 4 의 pr-author 는 새 브랜치를 따지 않는다. 커밋이 쌓인 기능
    브랜치로 PR 만 연다.
*   커밋이 하나뿐인 PR 은 커밋별 라운드를 따로 열지 않는다. 첫 종결 라운드가
    그것을 겸한다.
*   이미 진행 중인 PR 은 다음 커밋부터 적용한다. 앞 커밋의 검수를 다시 열지
    않는다.
*   종결 라운드에서 나온 CRITICAL/HIGH 는 앞 커밋을 고쳐 쓰지 않고 그 위에 수정
    커밋을 얹어 고친다.
*   커밋별 산출물은 이름이 다르다 — `phase3-review-c<N>-r<M>.md`,
    `verify-<원지적 출처>-<n>-c<N>-r<M>.md`. pr-author·pr-reviewer 의 입력은
    종결 라운드의 산출물뿐이다.

**그대로인 것:** 듀얼 리뷰 구성(cc + codex 동시, 모델·effort 고정, 임의 하향
금지), 싱글턴 교차 검증, 라운드 보고, 변경 설명, 완료 감사, Phase 2 의 종결
조건(`[구조]` CRITICAL/HIGH 0), Phase 4 의 규약.

**바뀐 자리:** `template/.claude/skills/harness-orchestrator/SKILL.md` 에 문단을
끼워 넣었다(기존 줄은 고치지 않았다).

*   "종결 기준·라운드 규약" 안, "라운드 보고" 소절 앞에 새 소절 "적용 단위".
*   "Phase 2" 절 끝에 "계획 게이트가 닫힌 뒤" 한 문단.
*   "Phase 3" 절 끝에 "여러 커밋으로 나눠 개발하는 PR" 한 문단.
*   "Phase 4" 절 끝에 "여러 커밋으로 나눠 개발한 PR" 한 문단.
*   "싱글턴 지적 교차 검증" 절 (9) 에 C(커밋별 산출물 이름)와, "데이터 전달"
    절에 한 줄.

`template/.claude/agents/pr-author.md` 의 "작업 순서" 뒤에도 같은 예외를 한
문단으로 끼워 넣었다. `docs/decisions/2026-08-01-dual-review-rule.md` 의 "후속
이력"에는 이 결정을 한 항으로 더했다.

## 조사가 말한 것

쓰임새 등급을 함께 적는다. `[관행]` 은 "그렇게 운영하는 곳이 있다"까지만
받친다. 사람 리뷰의 수치는 피로·시간 기제에서 나온 값이라 LLM 에 수치로 옮기지
않는다.

### 결정 1 의 근거 — 관행이 일치한다

*   `[관행]` PEP 1 — 수락된 PEP 는 실질적으로 고치지 않되, 구현 경험으로 바뀐
    점은 적어서 최종 시점에 구현을 정확히 기술하게 한다.
    <https://peps.python.org/pep-0001/>
*   `[관행]` Rust RFC — 수락 뒤에는 실질 변경을 하지 않는다. 큰 변경은 새 RFC
    로 쓴다. <https://github.com/rust-lang/rfcs>
*   `[관행]` Ubl(2020), "Design Docs at Google" — 구현 중 설계가 바뀌면 출시
    전에 문서를 갱신한다.
    <https://www.industrialempathy.com/posts/design-docs-at-google/>

LLM 으로 잰 자료는 없다. 끝에 맞춘 계획서를 다시 리뷰해야 하는지도 선례가
없다.

### 결정 2 의 근거 — 검사 문헌이 받치고, 반대 방향 실측이 하나 있다

*   `[관행]` NASA-STD-8739.9 — 중대 결함은 반드시 고치고 비중대 결함은 중재자
    재량으로 고친다(6.3.8). 후속 확인은 수정 완료와 새 결함 미유입을 함께
    본다(6.3.10.1).
    <https://standards.nasa.gov/sites/default/files/standards/NASA/Baseline/1/nasa-std-87399_with_change_1.pdf>
*   `[관행]` Fagan(1976) — 후속 확인의 목적은 수정이 올바르게 적용됐는지 보는
    것이다. DOI 10.1147/sj.153.0182
*   `[관행]` 리눅스 커널 — 패치가 크게 바뀌면 받은 리뷰 태그를 뗀다.
    <https://www.kernel.org/doc/html/latest/process/submitting-patches.html>
*   `[LLM 효과]` LLM 은 심각도가 높은 결함을 더 잘 잡는다(Critical 0.52,
    Minor 0.40). CRITICAL/HIGH 부터 고치는 쪽을 받친다. MCR-Bench, ISSTA
    2026, arXiv 2608.27442.
*   `[유비]` LLM 수리를 되풀이하면 통과하던 점검이 깨지는 회귀가 난다. 회귀가
    난 수리는 코드 변경량이 2.6배였다. 수정분을 다시 확인할 까닭이다.
    Agyekum·Santos, ESEM 2026, arXiv 2608.13404.
*   `[LLM 효과]` **반대 방향:** 같은 변경을 서로 독립으로 여러 번 리뷰해
    모으면 재현율이 두 배를 넘게 오른다. 곧 1라운드가 놓치는 것이 적지 않다.
    표본 PR 은 평균 약 180줄이다. SWR-Bench, PACMSE(FSE) 2026, DOI
    10.1145/3808144.

### 결정 3 의 근거 — 직접 근거가 없다

재수집 뒤에도 찾지 못한 것이 넷이다.

*   1만 줄 이상 입력에서 LLM 코드 리뷰의 재현율을 크기별로 잰 자료. 확인한
    벤치마크의 입력은 모두 평균 수백 줄 아래다.
*   같은 PR 을 조각으로 볼 때와 전체로 볼 때를 견준 코드 리뷰 실측.
*   서로의 보고를 보지 않는 두 회사 LLM 의 지적을 합친 실측.
*   "지적 없는 라운드 N회 연속"을 종료 기준으로 쓴 선례.

받치는 쪽이 하나 있다. "라운드"의 뜻이 결과의 방향을 가른다.

*   `[LLM 효과]` 서로 독립인 새 실행을 모으면 재현율이 오른다(위 SWR-Bench).
    한 대화에 이력이 쌓이면 성능이 떨어진다 — 다회차 리뷰에서 라운드가 늘수록
    결함 발견이 줄었고(MCR-Bench), 다회차 대화는 평균 39% 나빠졌다(Laban 외,
    ICLR 2026, arXiv 2505.06120). 종결 라운드는 리뷰어가 매번 새 컨텍스트로
    시작하므로 앞쪽에 가깝다.

알려진 약점은 여럿이다.

*   `[LLM 효과]` 긴 입력에서는 가운데 있는 정보가 묻힌다. Liu 외(2024), TACL,
    DOI 10.1162/tacl_a_00638. 입력 길이만으로도 성능이 떨어진다. Du 외,
    Findings of EMNLP 2025, DOI 10.18653/v1/2025.findings-emnlp.1264. 두 연구의
    과제는 리뷰가 아니라 질의응답·수학·코드 생성이다.
*   `[LLM 효과]` 변경 여럿을 한 창에 모아 보여 주면 PR 하나씩 볼 때보다
    탐지율이 39–45%p 떨어졌다. 과제는 코드 리뷰가 아니라 보안 감사다.
    PRWeaver, 프리프린트, arXiv 2608.02693.
*   `[메커니즘]` 리뷰 도구는 예산을 넘는 파일을 통째로 뺀다. PR-Agent 문서.
    <https://github.com/The-PR-Agent/pr-agent>
*   `[LLM 효과]` 다회차 리뷰의 오탐 가운데 가장 많은 것이 이미 해결된 결함을
    새로 다시 지적한 것이었다(32.5%). MCR-Bench.
*   `[LLM 효과]` 회사가 다른 모델끼리도 오류가 겹치고, 능력이 클수록 더
    겹친다. 두 리뷰어가 함께 놓치는 자리가 있다는 뜻이다. Kim 외, ICML 2025,
    arXiv 2506.07962. Goel 외, ICML 2025, arXiv 2502.04313. 앞 연구의 과제는
    객관식 문항이다.
*   `[LLM 효과]` LLM 판정자는 "문제 없음" 쪽으로 기운다. Jain 외, arXiv
    2510.11822. 반대로 옳은 코드를 결함으로 모는 편향도 있다. Jin·Chen(2026),
    DOI 10.1007/s10515-026-00638-5.

### 근거 없이 정한 것

아래는 선례가 아니라 이 프로젝트의 실측과 kty 의 판단으로 정했다.

1.  종결의 3이라는 수. 3회는 수렴을 확인하는 장치이지 품질을 보증하는 수치가
    아니다.
1.  종결 입력을 PR 전체 한 덩어리로 넣는 것. 위 "알려진 약점"은 이것과 반대
    방향이다.
1.  커밋마다 1라운드면 충분하다는 것.
1.  MEDIUM/LOW 를 PR 단계로 미뤄도 잃는 것이 없다는 것. LLM 은 낮은 심각도
    결함을 덜 잡으므로 이것도 반대 방향의 근거가 있다.
1.  확인 패스를 두 번까지만 돌리고 회부하는 것의 2라는 수.
1.  두 회사 LLM 의 동시 리뷰가 한 모델을 되풀이하는 것보다 낫다는 것.

### 조사에서 나온 보완책과 처분

넣지 않았다 — 넣으려면 따로 정한다. "조사의 권고" 열은 평가 보고의 판정
표(1차 4.2절, 재평가 5.1·5.2절)를 옮긴 것이다.

| B | 종결 라운드가 넷을 따로 판정한다(커밋 사이 상호작용, 동기화 뒤 바뀐 부분, 이연 지적의 처분, 계획과 코드의 일치) | 필수 점검 목록으로 넣는다 | 뒤 둘은 결정 3 의 입력에 들어 있다. 앞 둘은 넣지 않았다 |
| C | 파일 순서를 바꿔 가며 다시 리뷰한다 | 순서 교대는 사용자 판단, 라운드 안 추가 패스는 넣지 않는다 | 넣지 않았다 |
| D | 한쪽이라도 CRITICAL/HIGH 면 통과 못 함, 리뷰어는 서로의 보고를 보지 않는다 | 넣는다(불일치 요구 프롬프트는 넣지 않는다) | 기존 규약이 같은 구조다(ADR-0019 · ADR-0020). 새 문구는 없다 |
| E | 수정 확인은 새 결함 유입도 보고, 수정이 크면 커밋 전체를 다시 본다 | 넣는다 | 확인 패스가 앞쪽이다. 뒤쪽(문턱)은 넣지 않았다 |
| F | 구현 중 바뀐 점을 끝에 한 번 계획 문서에 반영한다 | 넣는다 | 결정 1 이 이것이다. 덧붙이는 형식은 정하지 않았다 |
| G | 심각도 정의를 두 리뷰어에게 똑같이 준다 | 사용자 판단 | 기존 프롬프트 규약 그대로다 |
| H | 작성자가 리뷰 전에 안내 주석을 단다 | 넣지 않는다 | 넣지 않았다 |
| I | 두 리뷰어의 겹침으로 남은 결함 수를 추정한다 | 넣지 않는다 | 넣지 않았다 |
| J | 총 라운드 상한을 두고 넘으면 회부한다 | 넣는다(1차는 사용자 판단) | 기존 상한 5회를 종결 라운드에 그대로 쓴다 |
| K | 커밋별 라운드 안에서 여러 번 돌려 집계한다 | 사용자 판단 | 넣지 않았다 |
| L | 이미 처분한 지적의 재제기는 현재 코드 근거가 있을 때만 센다 | 넣는다 | 넣지 않았다 |
| M | 종결 라운드 리뷰어는 새 컨텍스트로 시작하고 처분표만 받는다 | 넣는다(현행의 명문화) | 넣지 않았다. 운영은 이미 이렇게 한다 |
| N | CRITICAL/HIGH 지적에 실행 근거를 요구한다 | 사용자 판단 | 넣지 않았다 |

## Alternatives Considered

**A. 현상 유지 — 커밋마다 무지적 3회, 커밋마다 계획 동기**

*   Pros: 커밋 하나하나가 가장 깊게 검수된다. 계획서가 늘 코드와 같다.
*   Cons: 라운드 수가 커밋 수에 곱해진다. Context 의 88시간이 이 방식이다.
*   Why not: kty 가 병목으로 지목했다. 계획 라운드 20시간은 코드가 아니라
    문서를 맞추는 데 썼다.

**B. 앞 PR 방식 — 커밋별 라운드를 무지적 계수에 넣고 PR 전체 라운드는 한 번**

*   Pros: 가장 빠르다. 실측 약 30시간.
*   Cons: 커밋 하나의 차분만 본 라운드는 커밋 사이의 맞물림을 보지 못한다.
    그런 라운드 둘이 종결 계수를 채운다.
*   Why not: kty 가 고른 것은 "마지막 PR 때 리뷰를 많이 돌린다"다. 종결의 3회를
    전부 PR 전체로 채운다.

**C. 커밋별 검수를 없애고 PR 끝에서만 리뷰**

*   Pros: 커밋 단계의 비용이 0이다.
*   Cons: 큰 결함이 늦게 드러나 여러 커밋을 되돌린다. 작은 변경이 리뷰하기
    쉽다는 것은 사람 리뷰 문헌이 일관되게 말한다(Bosu 외 2015, DOI
    10.1109/MSR.2015.21).
*   Why not: 커밋마다 1라운드가 CRITICAL/HIGH 를 일찍 잡는다.

**D. 종결 라운드를 조각으로 나눠 리뷰하고 맞물림 패스를 따로 돈다**

*   Pros: 긴 입력의 약점을 피한다.
*   Cons: 라운드당 호출이 (조각 수 + 1) × 2 로 는다. 코드 리뷰에서 조각
    리뷰와 맞물림 패스의 효과를 잰 자료가 없고, 조각 크기를 정할 근거도
    없다.
*   Why not: kty 의 지시 밖이다. 조사는 넣기를 권했다(위 표 A). 넣을지는
    따로 정한다.

## Consequences

**Positive**

*   라운드 수가 커밋 수에 곱해지지 않는다. 커밋 단계는 1라운드와 확인 패스로
    끝난다.
*   계획 게이트가 개발 도중에 다시 열리지 않는다. 계획 문서를 맞추는 일이
    결정 대기를 만들지 않는다.
*   종결의 3회가 전부 PR 전체를 본다. 커밋 사이의 맞물림을 볼 기회가 세 번이다.

**Negative (못 막는 것은 못 막는다고 쓴다 — ADR-0011)**

*   **커밋 단계에서 놓친 결함은 끝에서 드러난다.** 그때는 앞 커밋 위에 수정
    커밋을 얹는다. 결함이 구조 부류면 여러 커밋을 고친다.
*   **이연한 MEDIUM/LOW 가 PR 끝에 몰린다.** 리뷰가 찾은 결함의 75%가 보이는
    기능에 영향이 없는 결함이었다는 연구가 있다(Mäntylä·Lassenius 2009, DOI
    10.1109/TSE.2008.71). 우리 MEDIUM/LOW 와 대체로 겹친다고 본다(추론이다).
    그 몫이 입력이 가장 큰 단계로 옮겨 간다.
*   **종결 라운드의 입력이 크다.** 위 "결정 3 의 근거"가 말하듯 이 크기에서
    리뷰가 얼마나 잡는지는 잰 자료가 없고, 인접 자료는 큰 입력에서 탐지가
    떨어진다고 말한다. 리뷰어가 무엇을 읽지 않았는지도 규약이 확인하지
    않는다.
*   **지적 없는 라운드 3회는 품질 보증이 아니다.** 두 리뷰어가 함께 놓치는
    자리가 있고, 여러 번 모아도 남는 결함이 있다. 3회는 수렴을 확인할 뿐이다.
*   **커밋별 작업 지시의 구조 결함은 계획 게이트가 아니라 그 커밋의 코드
    검수에서 드러난다.** 계획 게이트보다 늦다.
*   **커밋별 라운드의 싱글턴 처리는 사후에 대조하는 주체가 없다.**
    pr-reviewer 는 종결 라운드의 산출물만 받는다. 커밋 라운드에서 교차 검증
    없이 기각된 지적은 종결 라운드가 같은 지적을 다시 내지 않으면 드러나지
    않는다.
*   **전부 산문 계약이다.** 기계는 적용 단위를 모른다. 종료 훅은 전과 같이
    codex 산출물의 실존만 본다.
