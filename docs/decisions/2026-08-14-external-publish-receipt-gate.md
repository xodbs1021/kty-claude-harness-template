# ADR-0018 — 외부 발행 게이트: 리뷰 영수증 + 고위험 kty 승인

- 날짜: 2026-08-14 (구현·문서 확정 2026-08-15)
- 상태: 채택 (**등재 0건으로 출하** — 아래 "지금 상태" 참조)
- 관련: ADR-0005(커밋 분할) · ADR-0007(게이트 범위=파일 정체성) · ADR-0008(harness.env 판독 계약) · ADR-0011(자기규율 게이트=방지턱) · ADR-0013·0015(머리 표명) · ADR-0016(판독 실패를 조용한 생략으로 만들지 않는다) · ADR-0017(codex MCP 가드)

## 맥락

2026-08-14 실사고: 리뷰를 거치지 않은 내용이 **외부로 발행됐다**(이슈·코멘트 계열 MCP 도구). 완료 게이트 5종은 전부 저장소 안의 산출물을 보고, 발행은 그 바깥으로 나가는 행위라 어떤 게이트도 지나지 않았다. 원인 유형은 위조가 아니라 **누락**이다 — 리뷰를 안 한 게 아니라, 리뷰와 발행이 아무 데서도 묶여 있지 않았다.

## 결정

등재된 발행 도구의 호출 앞에 **리뷰 영수증**을 요구한다. 고위험(tier2)과 **모든 재발행**에는 kty 승인 소비를 추가로 요구한다.

- `guard-publish-receipt.sh`(PreToolUse, 매처 `mcp__.*|.*Artifact.*`)가 판정한다. 판정 16단의 **순서가 계약**이며 훅 첫머리 주석에 순서와 "그 자리를 옮기면 생기는 결함"이 함께 적혀 있다.
- digest = `SHA-256(json.dumps({"schema_version":1,"tool_name":…,"tool_input":…,"artifact_sha256":…}, sort_keys=True, separators=(",",":"), ensure_ascii=True))`.
- 영수증 스키마는 **8필드 고정**(schema_version·tool_name·digest·tier·review_artifact·nonce·serializer_identity·issued_at). 누락도 미지 필드도 거부한다.
- 리뷰 산출물에 `발행-리뷰: tool=… digest=… tier=…` **3튜플**이 한 줄로 있어야 하고, 영수증의 tier 와 일치해야 한다. tier 는 발급자의 자유 입력이 아니다.
- 소비는 `ln`→`rm` 원자 claim 이다(`mv -n` 은 실패해도 rc=0 을 내는 구현이 있어 쓰지 않는다).
- 감사 흔적은 **발급이 아니라 소비 순간**에 남는다. 훅 자신이 `.needs-audit` 에 적으므로 Bash 로 손수 만든 영수증도 소비 시 반드시 관측된다.

### 지금 상태 — 등재 0건 (의도된 출하 형태)

`publish-registry.txt` 는 **활성 행 0개**로 나간다. 게이트는 배선돼 있고 계약도 전부 검증돼 있지만, 실제로 막는 도구는 아직 없다.

이유: 각 행은 **실세션에서 payload 를 캡처해야만 알 수 있는 사실**로 채워야 한다 — 도구 전체 이름, 본문·파일 경로 필드 이름, 훅 stdin 이 호출 원문인지, payload 에 float 이 실재하는지, 발급 환경과 훅 환경의 python3 정체성이 같은지. 이 PR 을 만든 환경에는 그 fixture 가 없다. 추측으로 적은 행은 게이트를 조용히 없애거나(이름 한 글자가 다르면 "미등재"로 접힌다) 정상 발행을 영영 막는다. 그래서 **모르는 것을 적지 않고, 모른다는 사실을 공시한다** — `docs/usage.md` 5절과 registry 파일 머리에 같은 내용이 있고, 파일 안에 등록 절차 체크리스트 7항을 두었다.

## 근거

### 왜 JCS(RFC 8785) 같은 표준 정규화를 쓰지 않나

세 불변식이 그 자리를 대신한다. 셋 다 깨지면 이 결정도 다시 봐야 한다.

1. **발급과 검증이 같은 함수다** — `_common.sh` 의 `publish_digest` 단일 구현을 발급기와 훅이 verbatim 으로 쓴다. RFC 8785 1절이 "정규화는 두 대안 중 하나"라고 적은 바로 그 대안이다(같은 구조를 RFC 7515 5.3절에서 **유추**했다 — 원문 문맥은 문자열 대소문자라 라벨을 붙여 둔다).
2. **엄격 파서가 중복 키·비정수 수를 거부한다** — RFC 8785 의 실패원 목록이 근거다. **보장 범위는 "훅 stdin 에 남아 있는 중복"까지다**: 도구 제공자가 우리보다 먼저 payload 를 정규화했다면 원본 wire 의 중복은 이미 소실됐을 수 있다. 중첩 JSON **문자열** 내부도 대상이 아니다.
3. **드리프트는 정체성으로 잡는다** — 영수증에 `publish-digest/<계약버전> python3/<x.y.z>` 를 박고 소비 시점에 대조한다. 다르면 "직렬화 드리프트 의심"으로 막고 복구 경로를 안내한다.

### 조사 경위

`_workspace/rc-수집보고.md` 기준 **수집 31건 → 채택 18 · 기각 1(인용 교체 완료) · 보류 12(미인용)**. 채택분은 설계·계획 본문에 인용했고, 인용의 확실성 라벨을 함께 남겼다: RFC 7515 5.3 = **유추**, RC-12 = 2차 출처 + NVD 교차, GNU `mv` 이력 = **미확인**.

### 왜 tier 를 세 겹으로 묶나

리뷰어가 tier 를 자유롭게 적을 수 있으면 그 등급은 아무것도 아니다. 그래서 (a) 리뷰 산출물의 3튜플, (b) registry 의 `min_tier` 하한, (c) 규약의 "판정 불명 → tier2(fail-closed)" 셋으로 묶었다. **승인 요구는 registry 가 아니라 영수증 tier 가 정한다** — min_tier 는 하한일 뿐이라, 리뷰어가 2로 판정한 발행을 도구 분류가 되돌리지 못한다.

### 재발행 = 재승인

발행 API 가 실패했다는 **주장**은 훅이 검증할 수 없다. 그래서 `used/<digest>.*` 가 있으면 tier1 이어도 승인을 요구한다. rev3 까지 있던 retry token(PostToolUse 로 실패 응답을 관측해 재발급 토큰을 만드는 안)은 kty 확정으로 **이번 범위에서 제외**했다 — 도구별 오류 스키마를 모르는 채로 "실패"를 판정하면 그 판정 자체가 새 우회로가 된다.

### WAL(감사 선기록)과 감사자 계약

소비 **전에** `.needs-audit` 에 intent 를 적는다. 후기록으로 옮기면 기록이 실패했을 때 영수증만 소진되고 감사자에게는 발행이 없었던 것으로 보인다. 그래서 감사자 계약이 이렇게 읽는다: **intent 는 있는데 같은 이름의 `used/` 가 없으면 그 발행은 실행되지 않았다.** 면제도 같은 구조다 — **플래그 먼저, 로그 나중**이라 로그 기록에 실패하면 로그에는 아무것도 안 남고 플래그만 남으며, 그 플래그가 "면제를 시도했다(그리고 막혔다)"는 유일한 흔적이다.

### wedged 와 경합 정책

`ln` 은 성공했는데 `rm` 이 실패하면 `used/` 와 `active/` 에 같은 이름이 함께 남는다(**wedged**). 재claim 은 EEXIST 이고 발급기도 같은 digest 재발급을 거부하므로 **자동 복구가 없다** — 훅이 감사 표식을 남기고 수동 복구(quarantine 이동) 절차를 안내한다. 그리고 승인을 소비한 뒤 영수증 claim 에서 지면 **그 승인은 이미 소모됐다**: 메시지에 "재승인이 필요하다"를 반드시 싣는다(동시 경합은 희귀하지만, 조용히 끝나면 사용자는 승인이 살아 있다고 믿고 다시 시도해 또 막힌다).

승인 선택은 **파일명 사전순 단일 총순서**다. 비결정적으로 고르면 어느 승인이 소비됐는지 감사자가 재현할 수 없다.

## 수용한 한계 (전부 공시 — 사후 감사 영역)

- **자가 발급을 사전 차단할 수 없다.** 영수증·승인·면제를 만드는 손과 감시받는 손이 같다. 이것이 이 게이트의 위치다(ADR-0011 과 같은 자리 — 방지턱이지 방벽이 아니다).
- **Artifact TOCTOU** — 재해시 뒤 업로드 전에 파일이 바뀌는 창은 닫히지 않았다.
- Bash 의 `git push`·`gh`·`curl`, 사용자 대면 파일 전송은 사정권 밖이다.
- **신규·중립적 이름의 mutation 도구는 등록 전까지 무방비**다.
- 하네스 밖 디렉터리의 발행은 이 게이트를 지나지 않는다(프로젝트 층에만 배선 — kty 확정).
- registry 를 **슬롯**으로 둬 install/sync 가 덮지 않는다. 프로젝트가 등록한 행은 보존되지만 템플릿 쪽 주석 갱신은 전파되지 않는다.
- **폭발 반경**: 광역 매처(`mcp__.*|.*Artifact.*`)라 registry 한 파일의 오류(부재·형식 오류·중복 행)가 **그 매처에 걸리는 도구 전체**를 멈춘다. 매처는 과대 매칭이기도 하다 — 이름에 `Artifact` 가 들어가는 읽기 전용 도구에도 훅이 돈다(판정은 "미등재 → 통과"로 끝나지만, registry 가 깨지면 함께 막힌다). 좁히려면 실제 도구 이름이 필요하고, 그건 registry 를 채울 때 알게 된다. "모르는 상태의 통과"는 게이트 소멸이라 그 방향을 골랐고, 대신 전용 문구와 표준 탈출구 안내를 차단 메시지에 싣는다.
- **구 훅 잔존 + registry 부재 조합**이 가장 나쁘다(광역 차단). 롤백은 **배선 → 파일** 순서여야 하며 실행 가능한 명령 블록을 `docs/usage.md` 에 두었다.
- **python3 정체성 변경 시** 미소비 영수증 전량이 현 환경에서 소비 불가가 된다. 영구 무효는 아니다 — 환경 복원 또는 발급만 재실행(리뷰 재실행 불요)으로 복구하고, tier2 였다면 재승인이 필요하다.
- **입력 상한은 잠정값이다**: payload 1 MiB · Artifact 32 MiB. 이 값을 넘는 정상 발행이 있다면 그 발행은 **막힌다**. 실제 도구를 등록할 때 payload·산출물 크기를 재고 조정한다.
- **"멈춰서 무력화"의 잔여**: FIFO·비정규 파일·거대 입력은 막았지만, 훅이 정해진 시간을 넘겨 죽었을 때 Claude Code 가 그 호출을 **차단으로 보는지 통과로 보는지는 미확인**이다. 통과로 본다면 "훅을 느리게 만드는 것"이 곧 우회다. 검증 방법(실세션): 등재 도구를 하나 두고 훅 안에 인위적 지연을 넣어 timeout(15초)을 넘긴 뒤, 그 호출이 실제로 실행됐는지 발행물로 확인한다. 통과로 판정되면 상한을 더 낮추거나 게이트를 PostToolUse 감사와 병행해야 한다.
- **도구 이름 문자집합**: 게이트는 `[A-Za-z0-9_.-]` 밖의 이름을 가진 도구 호출을 **막는다**(판독값 오염과 구별할 수 없기 때문). 등록 가능한 이름의 문자집합과 같은 기준이라 판정이 갈리지는 않지만, 그런 이름의 도구를 쓰는 환경에서는 이 게이트를 끄거나 문자집합을 넓혀야 한다.
- p26(WAL 직전 재검사)·p51(claim 후 재대조)은 **정적 케이스**다. 다른 프로세스의 끼어듦과 하드링크 사본 조작을 러너 안에서 재현할 수 없어 "그 자리에 검사가 있는가"까지만 붙든다.

## 도메인 누출 예외 공시

층 경계 원칙(글루는 상위 층 구현을 모른다)에 대한 **의도적 예외**가 하나 있다: `publish-registry.txt` 에는 특정 벤더의 MCP 도구 이름이 들어간다. 도구 이름을 모르고 그 도구를 막을 방법은 없다. 완화 장치는 셋이다 — (a) 그 파일은 **슬롯**이라 프로젝트가 소유한다, (b) 훅·`_common.sh` 어디에도 도구 이름이 없다(전부 목록에서 읽는다), (c) 기계 검사(`scripts/check-layer-boundary.sh`)의 대상이 아님을 확인했다. 출하 시점 활성 행이 0개이므로 지금 저장소에는 벤더 이름이 한 줄도 없다.

## 영수증의 보존 위치

`_workspace/.receipts/` 는 **git 추적 대상이 아니다**(`.gitignore`). 감사 증거이지만 저장소에 올리지 않는다 — 발행 내용의 digest 와 리뷰 경로가 커밋 이력에 영구히 남는 것은 이 게이트가 요구하는 바가 아니고, 영수증은 그 기기의 작업 상태이지 공유 산출물이 아니다. 로컬에서는 `used/`·`approval-used/` 를 **무기한 보존**하고, 감사자는 그 디렉터리와 `.claude/.needs-audit` 플래그를 함께 읽는다. 대가: 다른 기기·CI 에서는 과거 영수증을 볼 수 없다(그 기기에서 소비된 것은 그 기기의 플래그와 발행물로 대조한다).

## 검수 1차 반영 (2026-08-15)

구현 직후 검수에서 **실측 재현된** 결함 다섯 부류를 닫았다. 전부 "깨끗한 환경에서는 초록으로 보이던" 축이다.

1. **환경 잡음이 게이트를 지웠다** — 도구 이름 판독기가 진단을 stdout 으로 합쳐(`2>&1`), 깨진 `.pth` 하나가 뱉는 오류가 그대로 도구 이름이 됐다. 그 이름은 목록에 없으니 "미등재 → 통과". 진단을 분리하고, 잡음이 stdout 으로 나오는 환경까지 대비해 호출부가 판독값의 **형태**를 한 번 더 본다.
2. **공백이 든 경로에서 재발행 차단이 사라졌다** — 비인용 글로브가 워드 스플리팅돼 `used/` 열거가 0건이 됐고, 0건은 이 훅에서 "재발행이 아니다"라는 뜻이다. 인용 글로브로 바꾸고, **"못 읽는다"와 "0건"을 갈랐다**(권한 오류가 fail-open 이던 자리).
3. **멈춰서 무력화** — Artifact 경로에 FIFO 를 주면 훅이 영원히 멈췄다. 멈춘 훅은 차단도 통과도 아니다. 일반 파일만 열고, 크기 상한을 두고 스트리밍으로 해시하며, payload 에도 상한을 뒀다.
4. **차단 메시지 위조** — payload·영수증에서 온 문자열이 무가공으로 나가 제어열로 가짜 하네스 줄을 만들 수 있었다. 출력 정화 + 영수증 필드 문자집합 제약 두 겹으로 막았다.
5. **등급·소비의 빈틈** — 3튜플이 "존재"만 검사돼 리뷰 하나에 두 등급을 적어 두고 낮은 쪽으로 통과할 수 있었고(정확히 1회로 정정), 승인 claim 의 `rm` 실패가 무시돼 잔존 승인이 다음 승인까지 봉쇄했으며(영수증과 대칭 처리), 발급기의 중복 검사가 비원자적이라 동시 발급으로 `active` 2개를 만들 수 있었다(digest 단위 락).

### 2차 재검수 반영 (같은 날)

1차 수정이 만든 결함 하나가 3축(보안·codex·Claude)에서 동시에 잡혔다. **`used/` 상태 판정을 명령 치환 안에서 했다** — 그 안의 차단은 서브셸만 죽이고 부모는 빈 문자열을 받아 계속 갔다. 차단 메시지가 두 번 찍히는데 종료 코드는 0 이고, tier1 재발행이 재승인 없이 통과했다(`chmod 300 used/` 한 번으로 재현). 판정과 차단을 본셸로 되돌렸고, 회귀 케이스의 픽스처도 `chmod 000`(다른 사유로 우연히 초록이던 값)에서 **`chmod 300`** 으로 바꿨다. **차단을 서브셸에서 하면 차단이 아니다** — 이 저장소가 처음 만나는 형태의 fail-open 이라 변이(m45)로 고정했다.

함께 닫은 것: 정화가 ASCII 제어문자만 보고 유니코드 서식문자(U+2028·U+202E)를 통과시키던 자리, registry 실패 경로만 정화를 안 지나던 자리, Artifact 를 stat 한 뒤 open 사이에 바뀌는 창(open 후 `fstat` 재검사), 롤백 절차의 `! grep` 확인 줄이 `set -e` 면제라 무동작이던 자리, payload 상한이 문자 수로 세지고 후행 개행 하나가 경계를 새던 자리.

기각 2건: "등재 0 = 효력 0"(kty 확정 사항의 의도된 출하 상태 — 3곳 공시 확인) · "커밋 재분할"(재커밋 비용 > 이득, ADR-0005 근거는 가독성이므로 PR 본문에 커밋 구성 사유를 적는 것으로 갈음).
