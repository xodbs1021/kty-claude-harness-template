## Context

리뷰 게이트는 Claude 리뷰어 하나로 돌고 있었다. 문제는 **생성자와 리뷰어가 같은 모델**이면
맹점을 공유한다는 것이다 — 같은 훈련 분포에서 같은 것을 못 본다.

2026-08-01 POK-29 세션에서 그 공백이 실측됐다. Claude 가 3라운드에 걸쳐 결함 7건을 잡고
**승인한** 설계에서 Codex 가 **추가 결함 5건**(이후 합본에서 3건 더)을 찾았고, 반대로 Codex
지적 일부는 Claude 가 이미 잡은 것과 겹쳤다 — 겹침은 상호 검증이고 차이는 순이득이었다
(근거: second-brain `Knowledge/dual-llm-code-review.md` "실증: 교차 리뷰가 잡은 것").

같은 날 두 번째 문제가 드러났다. 모델·effort 를 산문으로 고정해 두었더니 오케스트레이터가
"이번 확인은 작다"는 비용 판단으로 **스스로 effort 를 medium 으로 낮춰** 호출한 사고가
났다. 사용자가 명시한 표준을 AI 가 비용 판단으로 바꾼 것이다.

## Decision

**모든 리뷰 게이트를 Claude + Codex 이종(異種) 듀얼로 돌린다.** 대상은 plan-reviewer 의
설계·계획 각 pass(Phase 2), `ecc:code-reviewer` 검수(Phase 3), pr-reviewer 점검(Phase 4)
전부다. 아래는 커밋 `7709416`(듀얼 리뷰 전면화) 과 `cd0bfa6`(가드 훅) 에서 확인되는
그날의 규범 전부다. `--sandbox read-only` 는 `7709416` 이 **도입한 것이 아니라 승계한
것**이다 — 그 커밋의 pre-image(`7709416~1`) SKILL.md Phase 3 4번에 이미 `codex exec
--sandbox read-only` 로 적혀 있었다.

1. **병렬 독립 호출.** Claude 리뷰어 dispatch 와 병렬로 Codex 를 호출한다 — 서로의 결과를
   보고 쓰지 않는다(근거: `7709416` 이 대체한 옛 문구의 "**독립** 리뷰시킨다" — pre-image).
2. **호출 형태 고정:** `codex exec --sandbox read-only -m gpt-5.6-sol -c model_reasoning_effort="high" "<리뷰 프롬프트>"`
   (현행 형태는 후속 이력 참조 — 끝의 `< /dev/null` 은 2026-08-15 보수다).
   read-only 샌드박스라 Codex 는 쓰기 권한 자체가 없다(당시 호출 형태상 쓰기는 Claude 쪽에서만
   일어났다 — codex 를 개발에 쓸지에 대한 그날의 결정은 없다).
3. **모델 `gpt-5.6-sol` 하드코딩.** CLI 에 "최신 자동 추종" 메커니즘이 없음을 확인한 뒤
   사용자 지시로 고정했다. 새 세대 모델이 나오면 그 줄을 갱신한다.
4. **effort `high` 하드코딩 + 임의 하향 절대 금지.** 어떤 사유로도 오케스트레이터가 스스로
   낮출 수 없다. 낮출 필요가 보이면 실행 전에 사용자 승인을 받는다.
5. **기계 차단:** `guard-codex-invocation.sh`(PreToolUse) 가 모델·effort 미달 호출을
   exit 2 로 막는다. 훅 우회·삭제는 규율 위반이다.
6. **출처 태그로 통합:** `[cc]`(Claude 리뷰어) / `[cx]`(Codex) / `[cc·cx]`(둘 다 = 신뢰도
   높음, 우선 처리). **심각도 규칙은 출처와 무관하게 같다** — CRITICAL/HIGH 는 어느 쪽이
   잡았든 차단이다.
7. **판정 충돌 시 보류가 이긴다.** 단 보류 사유가 사실 오인이면 오케스트레이터가 근거를
   명시하고 기각할 수 있고, 기각 사유는 산출물에 기록한다.
8. **codex 미설치·미인증·호출 실패면** 해당 게이트를 Claude 단독으로 진행하되 보고에
   "듀얼 리뷰 생략(codex 실패)"을 명시한다 — 조용한 성공 위장 금지.

## Alternatives Considered

**A. Claude 리뷰어 단독 유지 (현상 유지)**
- Pros: 호출 비용·소요 시간이 절반. 통합 단계가 없어 파이프라인이 단순하다.
- Cons: 생성자와 리뷰어의 맹점이 겹친다. 실측이 이를 뒷받침한다 — Claude 가 3라운드 검토
  후 승인한 설계에서 Codex 가 추가 결함 5건(합본 3건 더)을 찾았다(second-brain
  `Knowledge/dual-llm-code-review.md` "실증: 교차 리뷰가 잡은 것").
- Why not: 검증 게이트의 존재 이유가 "놓친 것을 잡는 것"인데, 놓치는 축이 같으면 게이트가
  자기 복제다.

**B. 모델·effort 를 산문 규칙으로만 고정 (훅 없이)**
- Pros: 훅 유지보수 비용 0. 예외 상황에서 사람이 유연하게 판단할 수 있다.
- Cons: 같은 날 실제로 어겨졌다 — "작은 확인이니 낮추자"는 판단으로 effort 가 medium 으로
  내려간 사고가 기록됐다(같은 볼트 노트 "운영 규칙" 3번).
- Why not: 사용자가 명시한 표준은 AI 의 비용 판단으로 바뀔 수 없다. 산문 규칙은 어겨지므로
  PreToolUse 훅으로 기계 차단한다(`cd0bfa6`).

**C. 다수결(3개 이상 모델) 또는 두 모델의 자유 토의**
- **당시 논의 기록이 없다.** 2026-08-01 커밋·SKILL.md 어디에도 검토 흔적이 남아 있지
  않아, 기각 사유를 소급해 지어내지 않는다. 채택된 것은 "병렬 독립 + 보류 우선"이다.

## Consequences

**Positive**
- 한 모델이 승인한 산출물에서 다른 모델이 실질 결함을 찾는 일이 반복 관측됐다 — 특히
  "짧은 테스트는 통과하지만 장시간·장애 상황에서 터지는" 잠복 결함에서 효과가 컸다.
- 지적에 출처가 붙어 **어느 진영이 무엇을 보는가**가 데이터로 쌓인다. 2026-08-15 의 싱글턴
  교차 검증(ADR-0019)은 이 데이터가 있었기에 설계될 수 있었다.
- 모델·effort 가 훅으로 잠겨, 규율이 오케스트레이터의 선의에 의존하지 않는다.

**Negative (못 막는 것은 못 막는다고 쓴다 — ADR-0011)**
- **기계는 산출물의 실존만 본다.** 듀얼리뷰 게이트는 `_workspace/*codex*.md` 가 있는지만
  확인하므로 빈 껍데기 우회가 남는다(ADR-0017 에서 기록된 한계 그대로 이월).
- **MCP 경로의 일부는 미커버**다 — `mcp__codex__codex-reply`(기존 스레드 지속)·
  `base-instructions` 교체는 가드가 보지 않는다(ADR-0017).
- **codex 부재 환경에서는 규칙이 완화된다.** 단독 진행 + 명시로 정직성은 지키지만, 그 턴의
  검증 강도는 실제로 낮다. 이 완화는 싱글턴 교차 검증에도 그대로 전파된다(ADR-0019 ④).
- **비용·시간이 는다.** 라운드당 Codex 3~13만 토큰, 라운드 1회에 수 분~10분 단위.
- **레퍼런스 조사를 하지 않았다.** 소급 기록이라 지금 조사해도 2026-08-01 의 설계를 되돌릴
  수 없다(사후 지식으로 원결정을 덧칠하지 않는다는 이 문서의 원칙과도 충돌한다). 이 규칙을
  **개정할 때**는 조사 대상이다 — 다중 모델 리뷰·앙상블 검증의 공개 선례를 그때 본다.

  명시했다 — 범위가 없으면 Phase 2 의 새 상한(전면 3회)과 충돌해 읽힌다. Phase 2 교차 검증
  산출물 이름이 Phase 3 과 같은 `verify-<출처>-<n>[-r<N>].md` 임도 못박았다(명명 규약 절의 예시가
  Phase 3 파일만 들고 있어 흔들릴 자리였다).

  **근거 (2026-09-04 실측, pokeclip-mono POK-195 M4 계획 게이트):** 계획 듀얼 리뷰를 r1~r6 까지
  돌렸고 **6라운드 × 리뷰어 2 × 약 30만 토큰 + 싱글턴 교차 검증 ≈ 500만 토큰**이 들었다.
  라운드별로 잡힌 것의 **성격이 달랐다.**
  - **r2~r4 의 CRITICAL/HIGH = 구조 부류** — 동일성 축 선택 · 발행이 이벤트 루프를 막음 ·
    계수 이중 가산 · 동적 경로에 슬레이트 불가. 설계 단계에서 안 잡으면 **며칠치 재작업**이
    되는 것들이라 계획 라운드가 값을 했다.
  - **r5~r6 의 HIGH = 구현 세부 부류** — 어느 SQL · 어느 자리 · 트랜잭션 결속 · 캐시 갱신 자리.
    **6건 중 4건은 코드 작성·compose 실측·코드 리뷰가 더 싸게 잡는다.**

  즉 **HIGH 의 성격이 구현 세부로 내려온 시점이 계획 라운드의 손익분기점**이다. 무지적 3라운드는
  diff 가 실재해 "시나리오를 코드에서 재현한다"가 성립하는 코드·PR 단계에 남기고, 계획·설계
  단계는 되돌리기 비싼 결정(`[구조]`)만 0으로 만들고 닫는다.

  **감수하는 것(Negative):** `[세부]` HIGH 를 계획 단계에서 닫지 않으므로 **이월 3종 세트 중
  하나라도 빠지면 그 지적은 유실**된다 — 특히 Phase 3 검수 프롬프트 주입(3번)이 산문 계약이라
  기계가 확인하지 않는다. 또 부류 태그는 리뷰어의 판단이라 `[구조]`/`[세부]` 경계가 흔들릴 수
  있어 "갈리면 `[구조]` 로 올린다"를 보수 규칙으로 뒀고, 오케스트레이터의 `[구조]`→`[세부]`
  강등은 장부에 근거를 남기게 했다.
