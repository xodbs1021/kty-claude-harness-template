# ADR-0013: 지식 회수 정책 — 주소는 그대로, 트리거는 넓히고, 선택은 위임하고, 표명은 형식만 기계로

**Date**: 2026-08-10
**Status**: accepted — [ADR-0010](2026-08-06-knowledge-retrieval-policy.md) 을 supersede 한다
**Deciders**: 김태윤(갈림 4건 확정), Claude(설계·듀얼 검수 2라운드)

---

## Context

[ADR-0009](2026-08-06-profile-canon-upstream.md)가 배관을 깔았고 — 프로필 9절 진입점 슬롯, `ecc:architect`·`ecc:planner` 주입, 산출물 첫 줄의 `사전 결정 회수:` — [ADR-0010](2026-08-06-knowledge-retrieval-policy.md)이 그 위에 정책이 **없다**는 사실을 못박았다. 공백 4개: ① 트리거가 좁다 ② 선택 기준이 전무하다 ③ 표명과 실행이 분리돼 있다 ④ `claude-mem` 과의 분업이 미정이다.

이 ADR 이 그 넷을 닫는다. 설계 전문과 듀얼 검수(2라운드, 지적 전건 반영) 기록은 `_workspace/00_design-retrieval-policy.md`·`14_design_review_integrated.md` (근거 raw 는 상위 층 지식 저장소의 이 프로젝트 specs 에 보존).

**판정 프레임** — ADR-0012 ⑤·⑥절의 기준을 그대로 썼다: 지금 없는 것이 판단의 실패인가(→ 기계), 범위의 문제인가(→ 단순하게). 여기에 구분 하나를 보탠다. 이 저장소에는 겉보기에 충돌하는 규칙이 둘 있다 — *"실제로 새는 것을 본 뒤에만 방어를 늘린다"*(관측 우선)와 *"산문으로만 존재하는 절차는 훅·게이트로 승격하라"*(산문 승격). 구분 기준은 **의무가 이미 있는가**다. 관측 우선은 새 의무의 신설에, 산문 승격은 이미 계약인 의무의 집행에 적용된다.

용어를 갈라 쓴다 — ADR-0010 이 셋을 섞어 쓴 것이 혼선의 원인이었다: **주소**(어디 있나 — 진입점 경로), **트리거**(언제 읽나), **선택**(무엇을 읽나).

## Decision

### ① 주소 — 변경 없음

진입점 경로 하나(프로필 9절). ADR-0009 그대로다.

### ② 트리거 — 셋을 넓힌다

| 트리거 | 얻는 것 | 표명 |
|---|---|---|
| architect·planner 착수 전 (현행 유지) | 설계·계획이 선행 결정 위에서 시작 | 첫 줄 + 회수 블록 (기계 형식 검증 — ④) |
| **clarifier — 질문 전** (신설) | 과거 결정으로 답이 되는 질문이 사용자에게 안 간다. 질문이 소음이 되면 진짜 질문도 무시된다는 결정 게이트의 비용 논리와 같은 축 | 출력에 `사전 결정 회수:` 줄 — **산문 검증뿐** |
| **새 결정을 내리는 순간 — ADR 작성 전** (신설) | 같은 결정의 재결정·선행 결정과 모순되는 결정이 작성 전에 걸린다. ADR-0009 가 진단한 병("같은 결정을 매번 다시 내리고 그 재결정이 또 저장된다")을 정확히 겨눈다 | ADR "관련" 절에 선행 결정 인용(또는 `선행 결정 없음`) — pr-reviewer 점검 항목, **산문 검증뿐**. 첫 줄 표명은 요구하지 않는다(`# ADR-NNNN:` 형식이 이미 계약) |
| **developer — 주소만** (신설) | "이 부분 전에 어떻게 정했더라"가 나올 때 갈 곳이 생긴다 | 없음 — 의무가 아니다 |

**기각 둘.** developer 착수 전 **의무** 회수 — 계획서가 이미 회수된 지식을 담고 오므로 같은 지식을 층마다 다시 읽으면 토큰만 쓴다(ADR-0009 Alt C 사유 유지). "구현 중 질문"이 언제인지는 기계가 못 보는 판단이라, 주소를 주고 관측한다(새 의무 신설 = 관측 우선). 검수자 회수 — 검수 기준은 프로필 §4 불변식이 그 자리다. 선행 결정 중 검수에 걸릴 것은 §4 로 증류되는 것이 정본 경로다.

### ③ 선택 — 프로토콜만 계약화하고 판단은 위임한다

하네스는 "무엇을 찾는지"(디스패치 프롬프트의 작업 요약 — 이미 가진 정보)를 주고, 무엇을 읽을지는 진입점을 읽는 에이전트가 정한다. 대신 절차를 계약으로 고정한다:

```
1. 프로필 9절의 진입점을 읽는다.
2. 진입점이 목차·라우팅이면, 이번 작업과 관련된 항목만 따라가 읽는다. 전부 읽지 않는다.
3. 그 너머의 전문 탐색은 진입점 라우팅으로 부족할 때의 최후 수단이다(도구는 규정하지 않는다).
4. 무엇을 읽었고 무엇이 걸리는지를 회수 블록으로 낸다.
```

**층 경계 판정 기준** (ADR-0006 을 위반하지 않는 이유 — 검수에서 정련된 3문): ⑴ 하네스가 소유하는 공급자-중립 계약인가 ⑵ 구체 바인딩은 사용자 층에서 오는가 ⑶ 상위 층 구현을 바꿔도 하네스를 수정하지 않는가. 셋 다 예다 — 프로토콜이 가정하는 것은 "진입점은 진입점이다"라는 의미적 계약뿐이고, 특정 포맷 파싱도 구체 구조 이름도 없다. *"공개 포맷 의존은 층 위반이 아니다, 사유화된 배치 의존이 위반이다"* 라는 속기는 이 3문의 줄임이다 — 공개 포맷이라도 하네스가 고정 파싱하면 ⑶이 깨져 위반이다.

**전제**: 상위 층 CI 가 링크 무결성·인덱스 완전성·canon 포인터를 보장한다. 이 전제가 깨진 저장소에서는 회수 품질이 그만큼 내려가고 하네스는 감지하지 못한다.

**기계 필터(선택 자동화)는 만들지 않는다.** 기계 질의가 서려면 상위 층 frontmatter 스키마가 서야 하는데 실측이 반대다(타입별 스키마 미정의 — `status` 59%·`related-projects` 27% 누락, 대부분 "해당 없음"이라 필터를 못 짠다. 상위 층 실측이라 이 저장소에서 재검증 불가). 관측 없이 규약을 지어내는 것은 임의 목록 부류다.

### ④ 표명 — 두껍게 만들고, 형식만 기계로 검증한다

**내용의 기계 검증은 층 위반 없이는 불가능하다** — "읽었는가"를 기계가 확인하려면 하네스가 그 경로의 내용 구조를 알아야 한다(ADR-0009 Alt D 사유 유지). 못 푸는 것은 못 푼다고 적고, 세 단계로 올린다:

**⑴ 표명을 두껍게.** 산출물 첫 줄(`사전 결정 회수: <경로>` 또는 `없음(<사유>)`) 직후에 회수 블록: `- 걸리는 선행 결정: <제목 — 이번 작업에 어떻게 걸리는지 한 줄>` (0건이면 `걸리는 선행 결정 없음`). 지어낸 회수는 경로 한 줄보다 목록이 더 큰 거짓말이 되고, 검증 대상이 생긴다.

**⑵ 내용 검증은 검수 층으로 — 전부 산문 계약이다.** 검사 3항목(회수 블록 형식 / 산출물이 걸리는 선행 결정과 모순되는가 / 걸린다는 결정이 실제로 반영됐는가)을 plan-reviewer 점검 항목과 설계·계획 pass 의 codex 리뷰 프롬프트 계약에 얹는다. **기계 보장이 아니다** — `stop:dualreview` 게이트는 플래그만 보고, codex 산출물 실존도 plan-reviewer 실행도 기계가 확인하지 않는다. 기계가 보장하는 것은 "듀얼 리뷰를 마쳤다고 에이전트가 표명(플래그 삭제)했다"까지다. (설계 v2 가 "기계에 연결된 검증 축이 생긴다"고 적었다가 검수가 거짓 공시로 반증했다 — 그 철회를 여기 기록한다.)

**⑶ 형식 검증은 Stop 게이트로 — 신설 `stop:retrieval`.** 표명 첫 줄은 ADR-0009 가 만든 **이미 있는 계약**이고 그 검증이 산문("첫 줄을 확인한다 — 없으면 되돌린다")으로만 있었다 — 산문 승격 부류다. `_workspace/00_design*.md`·`01_plan*.md` 는 하네스 소유 산출물이라 층 위반이 없다.

```
mark-needs-audit: 설계·계획 산출물 저장 시 .needs-retrieval 에 경로 기록 (안=상대, 밖=절대)
stop 게이트 3.4: 각 경로의 첫 줄이 표명 형식인가 (BOM·CR 스트립 후 판정.
  상대경로는 $PROJECT_DIR 기준. 빈 파일·읽기 실패·접두어만 = 불량. 파일 소실 = 스킵.
  플래그 파일 읽기 실패 = 차단)
불량 0건 → 자동 해제. work_pending() 재평가로 남은 할 일이 없으면 exit 0
  (decision_note 가 있으면 systemMessage 로 방출 — ADR-0012 ② "경고를 삼키지 않는다"는
  성공 경로에도 적용된다)
불량 ≥1건 → 차단 + emit_decision_note + 불량 파일·사유 나열.
  예산 키 = "retrieval:<정렬된 불량 목록>" — 게이트 자신의 키에만 결합한다. 공유 지문
  flags_fp 에는 존재 비트만 넣는다(지문 불변식 "서 있는 플래그의 집합, 내용 아님" 유지)
```

- **자동 해제가 이 게이트의 형태다.** 결정 게이트가 "실제로 물으면 풀린다"이듯 이것은 "형식을 지키면 풀린다" — 지울 플래그를 에이전트 손에 주지 않는다.
- **fail-closed.** 위양성 비용이 메시지 한 번이다 — 집안 표준대로 기운다. 결정 게이트만 예외였던 이유(질문 소음)가 여기 없다.
- **`retrieval_pending()` 은 `knowledge_gate_active()` 와 의미가 다르다** — knowledge 는 env 스위치가 1차 오프 수단이고 훅 비활성은 호출부가 따로 보지만, retrieval 은 끄는 방법이 `ECC_DISABLED_HOOKS=stop:retrieval` 하나뿐이라 비활성이 곧 "할 일 없음"이다. 플래그 5종 중 이것만 그렇다.
- **`decision_armed` 에 넣지 않는다.** 설계·계획 편집은 항상 듀얼리뷰·지식 플래그를 함께 세우므로 정보 이득이 0이고, 소실 항목만 남은 stale 플래그가 결정 게이트(3.2 — 3.4 보다 앞이라 해제 기회가 없다)를 오발동시키는 결합만 남긴다.
- **검수 산출물 재귀는 명명 계약으로 막는다** — 듀얼 리뷰 규칙에 "리뷰 산출물 파일명은 `00_design`·`01_plan` 접두어를 쓰지 않는다". 훅 쪽 이름 제외(예: `codex` 포함 시 스킵)는 두지 않는다 — 관측되지 않은 재귀를 막으려고 실재하는 위음성(codex 를 다루는 정상 설계서의 무게이트)을 신설하는 것이라 기각했다.

**Stop 실행 순서 (계약 재기재):** push **탐지**(0) → 조기 종료(1, `work_pending()`) → 타입체크(3) → 결정(3.2) → **회수 표명(3.4)** → 듀얼리뷰(3.5) → 설명(4) → 지식(5) → push 차단(5.5) → 감사(6). 3.4 가 3.5 앞인 이유는 비용이다 — 표명 없는 산출물로 리뷰에 노력을 쓰기 전에 잡는다. 정확성 문제가 아니므로 옮기는 변이로 잰다.

### ⑤ `claude-mem` 과의 분업

- **진입점**: "전에 무엇을 **정했나**, 왜" — architect·planner 착수 전, clarifier 질문 전, ADR 작성 전.
- **claude-mem**: "전에 무엇을 **했나**, 비슷한 걸 풀었나" — Phase 0 착수 시 1회 검색(현행 유지).
- **충돌 시 진입점을 따르고, 어긋남 자체를 사용자에게 보고한다.** 근거는 진입점 너머의 성격(그건 하네스가 모른다)이 아니라 **사용자가 슬롯으로 지정했다는 사실**이다 — 슬롯에 넣은 것 자체가 "이쪽을 정본으로 참조하라"는 사용자 층의 바인딩이다.

## Alternatives Considered

### A. 상위 층이 회수 인터페이스("질의 → 경로 목록")를 제공한다
- **Pros**: 선택 품질에 계약이 생긴다. 층은 형식적으로 유지된다
- **Cons**: 상위 층에 새 규약·유지보수 의무가 생기고 하네스가 그 형식을 알아야 한다. frontmatter 실측(위 ③)이 기계 질의의 전제를 부정한다
- **Why not**: 관측 없이 규약을 지어내는 설계다. 실제로 새는 것을 본 뒤 재검토

### B. 현재 유지 — 품질 보장 없음을 공시만 한다 (ADR-0010 상태)
- **Pros**: 아무것도 안 만든다
- **Cons**: "알아서 읽어라"는 세션마다 다른 절차를 낳는다
- **Why not**: 절차의 부재는 판단 문제가 아니라 계약 부재라 비용 없이 닫을 수 있다

### C. `harness.env` 에 결정 경로 패턴 슬롯
- **Why not** (이월된 기각): 상위 층 CI 가 `canon-path` 를 이미 검증하므로 중복이고, 사용자가 패턴 목록을 유지보수하게 만들어 자동화 목적에 역행한다

### D. 회수를 전 에이전트 의무로
- **Why not**: ADR-0009 Alt C 그대로 — 같은 지식을 층마다 다시 읽으면 토큰만 쓰고 판단은 안 바뀐다

### E. 표명 형식 검증도 산문으로 둔다
- **Pros**: 게이트가 하나 안 는다
- **Cons**: 산문 절차의 불이행은 이 저장소가 반복 실측한 부류다(2026-08-02 볼트 반영 0회 이행 · 2026-08-03 듀얼리뷰 생략)
- **Why not**: 이미 계약인 의무의 집행 — 산문 승격 규칙의 적용 대상이다

## Consequences

### Positive
- 지식이 **읽히는** 방향이 트리거 넷을 얻는다 — 특히 "새 결정을 내리기 전"이라는, 재결정 병을 직접 겨누는 자리
- 회수 절차가 세션마다 재발명되지 않는다 — dispatch 계약이 프로토콜을 고정한다
- 표명 형식이 처음으로 기계에 걸린다 — "첫 줄 확인" 산문이 게이트가 된다
- ADR-0010 의 "배선만 있고 정책은 없다" 상태가 끝난다

### Negative — 이 정책이 못 막는 것 (별도 절)
- **읽었다는 사실 자체는 여전히 기계가 못 본다.** 형식 게이트는 "표명이 형식대로 있다"까지다. 회수 블록을 지어내는 에이전트는 검수 층(LLM)만 잡을 수 있고, 그것도 확률적이다.
- **내용 검증 3항목은 전부 산문 계약이다.** plan-reviewer 실행도 codex 프롬프트 준수도 기계가 강제하지 않는다.
- **선택 품질 보장 없음.** 진입점 너머 라우팅과 상위 층 CI 전제에 달렸고, 전제가 깨져도 하네스는 모른다.
- **삭제 우회는 기계로 안 막힌다.** 파일 소실 항목은 스킵되고, 듀얼리뷰 게이트는 산출물 실존을 검사하지 않는다(플래그만 본다). 실존 검증은 감사자 몫이다.
- **Write/Edit 도구 밖 생성(`bash cat > …`)은 게이트가 안 선다** — PostToolUse 앵커의 공통 한계(기존 게이트 4종과 동일).
- **clarifier·ADR 트리거의 표명은 산문 검증뿐이다** — 사후 판정 데이터가 약하다.
- **0바이트 플래그는 비활성이다**(기존 4종과 같은 `-s` 관용구). 기록 실패는 mark-needs-audit 가 쓰기 시점에 systemMessage 로 알린다.
- **서브에이전트가 직접 산출물을 저장하는 구성은 미실측.** 현 SKILL 은 오케스트레이터가 저장하므로 무관하지만, 그 구성을 도입하려면 PostToolUse 발화 여부를 먼저 실측해야 한다.
- **결정 문서를 `docs/decisions/` 밖에 두면 지식 게이트가 안 선다** (mark-needs-audit 공시의 이월) — 하네스는 자기가 규정한 경로만 안다. 다른 위치 인식은 상위 층 구현 지식이라 층 위반. 닫지 않고 공시 유지.
- **developer 의 실제 회수 습관은 관측 대상** — 안 읽어서 새는 실측이 나오면 그때 승격을 재검토한다.
- 불량 파일 집합이 바뀌면 retrieval 게이트 자신의 차단 카운터가 리셋된다(예산 키에 목록이 들어가므로). 상태가 바뀌는 것은 갇힘이 아니라는 push 상세와 같은 판단이다 — 공시.

## 기계적 장치

`tests/retrieval-attestation.test.sh` (EXPECTED_CASES 상수 고정) + CI 스텝 + 변이 하네스. 케이스 25종·변이 15종의 목록과 근거는 설계서 7절. 통과 기대 케이스 전부가 후속 게이트(감사) 도달 문구를 요구한다 — rc 단독 판정 금지. 기존 계약 자리 전수(`tests/mark-needs-audit.cases.sh`·`FLAG_NAMES`·README·usage.md)를 함께 갱신한다.
