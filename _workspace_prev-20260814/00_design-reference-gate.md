## 0. 요구 원문과 확정 요지

**kty 요구 원문 요지:** *"계획 세울 때 레퍼런스 조사를 강제했으면 한다. 내가 그냥 조사해오라고
했으면 너는 절대 Netflix 조사 안 했을 거다 — 라이브 스트리밍 서비스가 아니니까. 조사가
필요하다고 판단되는 지시사항에 대해서만, 기계적 게이트로 무조건 실시하게 할 수 있나?"*

**확정 설계 요지 (kty, 2026-08-10):** "조사가 필요한 지시인가"의 **판정은 기계 불가**(임의
목록 부류). 대신 판정의 **무표명 통과**를 기계로 막는다 — ADR-0013 과 같은 구조:

- 계획·설계 산출물에 `레퍼런스 조사: 조사함(<대상·출처>)` 또는 `불요(<사유>)` 표명 의무.
  **불요에도 사유 강제**가 핵심(조용한 스킵 불가화)
- Stop 게이트가 **형식만** 검사 (회수 게이트 3.4 와 같은 기계)
- 조사 계약에 **인접 도메인 포함** 명시 — "우리가 라이브면 VOD·저장·CDN 도 본다".
  실증: pokeclip 사이드카의 답이 "라이브 아닌 Netflix"가 아니라 **Netflix Live Origin**
  (2025-12 TechBlog — S3→KV 전환, payload chunking, segment-template manifest)에 있었다
- 조사 실행은 전역 에이전트 `research-collector`(수집) → `research-evaluator`(독립 검증)
- 검수(plan-reviewer·codex)가 **불요 사유의 타당성과 조사 품질**을 심사 (산문 계약 공시)

**판정 프레임 정합(ADR-0013 의 구분):** 이 표명은 **새 의무의 신설**이다 — 관측 우선 규칙의
적용 대상. 그 관측은 이미 있다: pokeclip 미디어 사이드카(DVR·S3) 설계에서 선행 기술 조사가
실제로 0회였고 kty 가 그 누락을 실물로 짚었다(위 계기 사례). "실제로 새는 것을 본 뒤"라는
전제가 충족됐으므로 의무 신설이 정당하다. 신설된 의무의 **형식 검증**은 그 순간부터
산문 승격 부류가 된다 — 산문 절차 불이행은 이 저장소가 반복 실측한 부류다(2026-08-02
볼트 반영 0회 · 2026-08-03 듀얼리뷰 생략 — ADR-0013 Alt E 와 같은 논거).

## 2. 용어 (ADR-0013 의 3분법을 이어받아 하나 보탠다)

- **판정**(조사가 필요한 지시인가) — 기계 불가. 산출물 작성자(architect·planner)와

- **심사**(불요 사유·조사 품질) — plan-reviewer·codex 검수 (산문 계약)

## 3. 결정 ① — 게이트 형태: 3.4 를 "산출물 머리 표명 게이트"로 일반화한다

3.4 게이트가 파일마다 검사하는 항목을 하나에서 둘로 늘린다: 첫 줄(회수 표명 — 현행 그대로)
+ **둘째 줄(레퍼런스 표명 — 신설)**. 신설 부품은 검사 항목 하나와 예산 키의 검사 종류
태그(아래)뿐이고, 상태기계는 전부 기존 것을 재사용한다:

| 상태기계 부품 | 재사용 방식 |
|---|---|
| 플래그 | `.needs-retrieval` 그대로 — 같은 파일 집합(`00_design*`·`01_plan*`), 같은 트리거, 같은 생명주기 |
| `work_pending`·조기 종료 | `retrieval_pending()` 그대로 — 신규 항 없음 |
| 공유 지문(`flags_fp`) | `r` 존재 비트 그대로 — 신규 비트 없음 |
| 예산 키 | `retrieval:<정렬된 불량 목록>` 유지하되 **목록 항목에 검사 종류 태그를 붙인다**: `<경로>#1`(첫 줄 불량)·`<경로>#2`(둘째 줄 불량). 근거는 아래 ③-2 |
| 자동 해제 + 재평가 + 지문 재계산 | 그대로 — "두 검사 모두 형식 준수(또는 소실뿐)"일 때만 해제 |
| `decision_armed` 비편입 | 그대로 (r17 계약 유지) |
| 개행 없는 마지막 줄(`\|\| [ -n ]`) | 플래그 파일 쪽 그대로 (r26) + **문서 둘째 줄 읽기에도 같은 관용구**(신설 — r41·m26 으로 잰다) |
| mark-needs-audit | **변경 없음** — 플래그 5종·기록 로직·`tests/mark-needs-audit.cases.sh` 동일. FLAG_NAMES 불변 (라운드 1 양 검수자가 실물 대조로 확인) |

**근거:**
- ADR-0012 ⑥ "범위→단순": 두 표명은 대상 파일·트리거·형태(머리 줄 접두어+내용)·해제
  의미(형식을 지키면 스스로 풀림)가 전부 동일하다. 다른 것은 검사하는 줄과 문법뿐이다 —
  이것은 게이트의 **범위**(무엇을 검사하나)이지 새 판정이 아니다.
- 신설안(`stop:reference` + `.needs-reference`)은 직전 세션 검수가 잡은 상태기계 결합
  전부를 다시 지나야 한다: work_pending 편입 · flags_fp 존재 비트 · 게이트별 예산 키 ·
  예산 소진 rm/changed 목록 · 자동 해제 후 재평가 · compute_flags_fp 재계산 ·
  decision_armed 비편입 · 플래그 마지막 줄 개행. 여덟 결합면 각각이 실측 결함이 났던
  자리다(`specs/2026-08-10-회수정책-검수-실측.md`). 같은 지뢰밭을 정보 이득 없이 두 번
  걷는 설계다.
- **대가 (공시):** `ECC_DISABLED_HOOKS=stop:retrieval` 하나로 두 표명 검사가 함께 꺼진다.
  개별 끄기는 불가능하다. 수용 근거: 두 표명은 같은 산출물의 같은 머리 블록이고, 게이트
  끄기는 상시 운영이 아니라 비상 탈출구다. 개별 끄기 수요가 실측되면 그때 분리를 재검토
  (관측 우선). 게이트 ID 는 `stop:retrieval` 을 유지한다 — 근거는 **저장소 밖 사용처**다
  (사용자 셸의 `ECC_DISABLED_HOOKS` 설정·CI 환경 변수 등 이 PR 이 갱신할 수 없는 자리에
  이 ID 가 박혀 있을 수 있다. r2 [cc] L5 — 저장소 안 문서는 이번에 전수 갱신되므로 "문서
  호환"은 근거가 못 된다). **이름이 계약보다 좁아졌다**는 사실(제0원칙 2 관점의 괴리)을
  usage.md 와 ADR-0015 Consequences 에 명기한다.

## 4. 결정 ② — 표명 자리: 머리 2줄 고정, 회수 블록은 셋째 줄부터

산출물 머리가 다음으로 고정된다:

```
1줄: 사전 결정 회수: <읽은 경로>            또는  사전 결정 회수: 없음(<사유>)
2줄: 레퍼런스 조사: 조사함(<대상·출처>)  |  불요(<사유>)  |  실패(<시도한 것 — 실패 사유>)
3줄~: - 걸리는 선행 결정: <제목 — 한 줄>     (0건이면 - 걸리는 선행 결정 없음)
```

**근거:**
- 첫 줄은 `사전 결정 회수:` 가 선점했다(ADR-0009·0013 — 배포된 계약, 옮기지 않는다).
- 회수 블록은 가변 길이(걸리는 결정 수만큼 불릿)라 "블록 다음 줄" 앵커는 기계 판정이
  성립하지 않는다. "N줄 이내" 스캔은 임의 숫자 부류(ADR-0012 ⑥). 파일 전체 스캔은 머리
  표명이라는 형태를 잃고 문서 아래 묻힌 표명을 허용한다. **둘째 줄 고정**만이 임의 숫자
  없는 결정적 앵커다.
- 회수 블록의 위치는 **산문 계약**(ADR-0013 ⑴ "첫 줄 직후")이고 기계는 첫 줄만 봤다 —
  블록을 셋째 줄로 옮기는 것은 산문 계약 텍스트의 갱신이며 기계 계약 변경이 아니다.
- **ADR-0013 에 역참조를 남긴다**([cc] M4): ADR-0013 의 "관련" 절에 *"④-⑴의 회수 블록
  위치('첫 줄 직후')는 ADR-0015 로 갱신됨 — 셋째 줄부터"* 한 줄을 추가한다(supersede
  아님 — 블록 형식·의미는 불변. ADR-0013 이 회수 프로토콜 정본으로 직접 읽히므로 본문
  단독으로 낡은 위치를 안내하면 안 된다).

**BOM·CR 처리:** BOM 은 파일 첫머리에만 오므로 첫 줄만 스트립(현행). CR 은 두 줄 모두
스트립(r25 의 짝으로 둘째 줄 CR 케이스 r36).

## 5. 결정 ③ — 형식 문법·검사 알고리즘·메시지 정책

### ③-1 문법 (닫힌 문법 — 이 밖은 전부 불량)

```
레퍼런스 조사:<SP*><변형><SP*>(<내용>)<SP*>
<변형> ::= 조사함 | 불요 | 실패          (정확 일치 — 꼬리 문자가 붙으면 불량)
<SP>   ::= ASCII 스페이스(0x20) | 탭(0x09)  — 이 둘뿐. 비ASCII 공백(U+3000 등)은 SP 가 아니다
<내용> ::= LC_ALL=C tr -d '[:space:]' 후 비어있지 않은 문자열 (내부 괄호 허용 — 마지막 `)` 가 닫는 괄호)
```

**결정론 고정**(r2 [cx] M): 내용 판정의 `tr` 은 `LC_ALL=C` 를 명시해 실행 환경 로케일과
무관하게 바이트 단위로 동작시킨다. 첫 줄의 기존 내용 판정에도 같은 접두를 붙인다 — ASCII
입력에서 동작 불변이고, 이국 로케일에서의 판정 흔들림만 없앤다. **내용 검사는 세 변형
공통의 단일 경로**로 구현한다(변형 case 분기 → 공통 괄호·내용 검사) — 변형별로 검사를
복제하면 한 변형만 검사가 빠지는 부류(r2 [cx] HIGH `실패()`)가 생긴다. r46 이 그 계약을
잰다.

- `조사함부족(x)` 같은 **변형 꼬리는 불량**이다([cc] M1 / [cx] #6) — 변형 추출은 `(` 앞
  조각을 잘라 꼬리 공백을 트림한 뒤 **정확 일치**로 판정한다. `조사함 (x)` 는 통과,
  `조사함X(x)` 는 불량
- 닫는 괄호 뒤에는 `<SP>` 만 허용 — 꼬리 잡음(`불요(x) 추가설명`)은 불량. 정보는 괄호
  안에 적는 닫힌 문법을 유지해야 "괄호 밖으로 사유를 빼는" 우회가 안 생긴다
- `<내용>` 판정은 첫 줄과 같은 관용구(`tr -d '[:space:]'`, C 로케일 바이트 단위)를 쓴다.
  **공시:** U+3000 같은 멀티바이트 공백만 든 괄호는 바이트 판정상 "내용 있음"으로
  통과한다 — 유니코드 공백 목록을 들고 다니는 것은 임의 목록 부류라 하지 않는다(검수 몫)
- `실패` 변형(사용자 확정 ⑤): "필요하다고 판단했으나 실행이 실패했다"를 **있는 그대로**
  적는 칸. `불요` 에 접으면 단어 뜻(필요 없음)과 실제(필요했지만 실패)가 어긋나 표명이
  거짓이 된다. 검수는 실패 사유의 타당성과 재시도 여부를 심사한다
- 전각 괄호(`（）`)·`불필요` 같은 유의어는 불량이다 — 세 단어와 반각 괄호만. 프로필
  9절과 usage.md 에 명기한다([cc] LOW)

**회수 표명(첫 줄)보다 검사가 두꺼운 이유:** 회수 표명의 정상형에는 자유 형식(`<경로>`)이
있어 "접두어+비어있지 않음"이 검사 가능한 최대치다. 레퍼런스 표명은 형식이 세 형태로
닫혀 있고, 핵심 요구(**불요에도 사유 강제**)가 정확히 "변형+괄호 내용" 깊이에서만
기계화된다 — 접두어 검사만 하면 `레퍼런스 조사: 불요` 가 통과해 사유 강제가 산문으로
밀린다. 내용의 **진실성**은 여전히 검수 몫이다(형식 검사의 상한 — ADR-0013 ④ 유지).

### ③-2 검사 알고리즘 (3.4 루프 내부 변경)

```
파일마다:
  머리 2줄을 한 블록 리다이렉트로 읽는다 (파일을 두 번 열지 않는다).
  1줄 판정: 현행 그대로 (BOM·CR 스트립 → 접두어 → 내용 비어있지 않음). 불량이면 목록에 `<경로>#1`
  2줄 판정: CR 스트립 → 접두어 `레퍼런스 조사:` → ③-1 문법. 불량이면 목록에 `<경로>#2`
  (한 파일이 두 줄 다 불량이면 두 항목 — 메시지에는 각 사유가 따로 실린다)
```

**둘째 줄 누락 판정의 rc 소비 방식** (r2 [cc] H1 — 관용구를 옮겨 적는 것이 아니라 rc 를
실제로 소비해야 방어가 산다):

```sh
ref_missing=0; rline2=""
if IFS= read -r rline2; then
  :                                  # 개행으로 끝난 둘째 줄
elif [ -n "$rline2" ]; then
  :                                  # 개행 없는 마지막 줄 — read 가 rc=1 을 내고도 값을 담는다
else
  ref_missing=1                      # rc!=0 이고 값도 없다 = 둘째 줄이 없다 (1줄 파일)
fi
```

- `ref_missing=1` → 불량 사유 "둘째 줄 없음(레퍼런스 표명 누락)"
- rc=0 인데 빈 문자열(개행만 있는 둘째 줄) → 문법 경로로 들어가 **접두어 사유**로
  떨어진다(별도 사유 상수를 두지 않는다 — r3 [cc] 기록 항목의 서술 정합)
- **m26 은 `elif [ -n "$rline2" ]` 가지를 제거**한다 → 개행 없는 정상 둘째 줄이 "누락"으로
  오판돼 r41 이 빨개진다. v2 가 적었던 한 줄 관용구(`read || [ -n ]`)는 단발 read 에서
  rc 를 아무도 소비하지 않아 no-op 이었다([cc] r2 H1 적발 — while 루프 조건이었던 원본과
  자리가 다르다). 이 분기 구조가 그 정정이다

**불량 사유 문구(상수 — 테스트가 결합할 문자열)** (r2 [cc] M5):

**인접 도메인 계약(조사 지시문에 상수로 포함):** *"대상 도메인과 정확히 일치하는 사례만
찾지 마라. 인접 도메인 — 같은 문제를 다른 제약에서 푼 시스템 — 을 포함하라. 우리가
라이브 스트리밍이면 VOD·저장·CDN 도 본다. 실증: pokeclip 사이드카의 답은 '라이브가 아닌
Netflix'를 제외했으면 못 찾았다(Netflix Live Origin, 2025-12)."*

**왜 실행 주체가 오케스트레이터인가:** `ecc:architect`·`ecc:planner` 는 Read·Grep·Glob
만 가진 참조 에이전트라 웹 검색·에이전트 dispatch 를 못 한다(ECC 정의 기준 — 저장소 밖
정의이므로 환경별 차이는 dispatch 계약이 아니라 도구 실측이 정본). 조사 실행은 도구를
가진 오케스트레이터의 일이고, 판정·표명은 산출물 작성자의 일이다 — 표명이 작성자 손에
있어야 검수가 "작성자의 판단"을 심사할 수 있다.

**결정 게이트(3.2) 위양성 완화 계약**([cc] H5): 불요·실패 사유를 사용자 보고·대화에
인용할 때는 **백틱 또는 따옴표로 감싼다** — 결정 게이트의 구조적 제외 장치를 쓰는 정상
형태다. 사유 문장("~라서 조사하지 않았습니다")을 맨몸으로 서술하면 표지 어휘·서술형
종결에 걸릴 수 있다. 위양성 증가 자체는 8절에 공시한다.

### ⑥-2 검수 계약 — 레퍼런스 검증 3항목 (회수 검증 3항목의 짝)

**plan-reviewer 의 점검 항목 실물(`template/.claude/agents/plan-reviewer.md` 의 회수 검증
항목 옆)과** 설계·계획 pass 의 codex 리뷰 프롬프트(SKILL 듀얼 리뷰 규칙)에 추가:

1. 레퍼런스 표명이 형식대로 있는가 (둘째 줄, 세 변형 중 하나)
2. **불요 사유가 타당한가** — 특히 인접 도메인을 좁게 잘라 불요로 넘기지 않았는가
   ("라이브가 아니라고 Netflix 를 빼는" 부류를 명시 심사). 실패면 사유·재시도 필요성 심사
3. 조사함이면 그 조사가 설계·계획 본문에 실제로 반영·인용됐는가 (표명만 있고 본문이
   무관하면 지어낸 조사다). 출처가 재검증 가능한 지시자(URL·문서·수집물 경로)인가

**전부 산문 계약이다** — 프롬프트에 넣었는지는 기계가 확인하지 않는다(ADR-0013 ④-⑵ 와
동일한 공시).

### ⑥-3 조사 산출물 — 이름을 규정하지 않는다 (사용자 확정 ④)

## 8. 이 설계가 못 막는 것 (공시 — ADR-0015 에 그대로)

- **조사했다는 사실 자체는 기계가 못 본다.** `조사함(지어낸 출처)` 는 형식을 통과한다 —
  검수(산문·확률적)와 감사자 몫. ADR-0013 의 같은 공시의 연장
- **출처가 아예 없어도 통과한다**([cx] #9) — `조사함(Netflix)` 처럼 대상만 적은 표명도
  기계는 형식으로만 본다. 출처 요구는 검수 항목 3(⑥-2)
- **불요·실패 사유의 타당성은 기계가 못 본다.** `불요(시간 없음)` 도 형식 통과
- **조사 실행(collector→evaluator)은 기계가 강제하지 않는다** — dispatch 여부·품질·재수집
  1회 한정·실패 접기 전부 산문 계약
- **예산 소진은 두 표명을 함께 면제한다**([cc] M5) — 같은 지점 3회 차단 후 벽돌 방지
  통과가 `.needs-retrieval` 을 포함한 플래그를 전삭제한다. 기존 게이트 공통의 트레이드오프
  이고, #1/#2 태그가 "부분 진전인데 소진"의 한 경로를 닫았지만 진전 없는 3회는 여전히
  통과다(그 턴의 완료 주장 불신 경고 동반)
- **`00_design*`·`01_plan*` 이름 밖 산출물은 두 표명 모두 면제된다**([cc] M5) —
  mark-needs-audit 의 이름 계약 이월(ADR-0013 공시와 동일 부류)
- **`stop:retrieval` 하나로 두 표명이 함께 꺼진다** — 개별 끄기 불가(수요 관측 시 재검토).
  게이트 ID 이름이 계약보다 좁다는 괴리 포함
- **결정 게이트(3.2) 위양성이 구조적으로 는다**([cc] H5) — 불요·실패 사유 서술문("~라서
  안 했습니다")이 표지 어휘에 걸릴 수 있다. 완화는 인용 감싸기 계약(⑥-1)이고, 걸리면
  질문 한 번이면 풀린다
- **r04(0바이트 파일)는 두 검사의 격리 예외다**(③-A) — 0바이트 파일은 본질적으로 두
  검사 동시 불량이라 단독 변이를 두지 않는다. 단 첫 줄 "빈 줄" 분기 자체는 r50(첫 줄만
  빈 줄·둘째 줄 정상)+m35 가 격리 측정한다 — 예외는 0바이트 시나리오 하나로 좁다
- 삭제 우회·도구 밖 생성(`bash cat >`)·서브에이전트 직접 저장 미실측 — 기존 3.4 공시 이월
- clarifier·ADR 트리거에는 레퍼런스 표명 의무가 **없다** — 범위를 설계·계획 산출물로
  좁게 시작(새 의무 신설은 관측 우선). 새는 실측이 나오면 확장 재검토
- 표명 리터럴이 한국어다 — 하네스 소유 계약 문자열이라 발화 언어와 무관하게 유효하나,
  세 단어·반각 괄호 밖 유의어(`불필요`·전각 괄호)는 불량 판정된다(메시지가 형식 전문
  안내). 유니코드 공백만 든 괄호는 통과한다(③-1 공시)
- 배포 시점 어긋남: 훅은 세션 시작 스냅샷이라, sync 직후 세션에는 구 게이트(1줄 검사)가
  돌고 새 SKILL 이 2줄을 쓴다 — 새 산출물은 구 게이트도 통과하므로 무해(1줄 검사는 머리
  계약의 부분집합). 역방향(새 훅+구 SKILL 산출물)은 차단 후 메시지가 안내한다 —
  ADR-0013 과 같은 롤아웃

## 9. 검수 비수렴 기준 (착수 시 못박음 — 인계 5절)

① 수정마다 새 차단급이 나오고 ② 결함 폭이 좁아지지 않으면 — 둘 다 참일 때 성격으로
갈라 닫는다(계약 위반만 고치고, 취향·재설계 요구는 사유와 함께 기각 기록).

## 10. 선례 검토 (r2 [cc] M6 — 이 설계서 자신의 표명을 조사함으로 바꾼 근거)

v2 까지 이 설계서의 레퍼런스 표명은 `불요` 였다 — "이 저장소 고유 기계라 외부 선례가
새 정보를 주지 않는다". 검수가 이 사유 자체를 검수 항목 2("인접 도메인을 좁게 잘라
불요로 넘기지 않았는가")의 위반 실례로 적발하고 직접 선례를 제시했다. 검토 결과:

- **Rust RFC 템플릿의 필수 "Prior art" 절** — 제안 문서에 선례 조사 절을 의무화하고,
  내용 심사는 리뷰어가 한다. 이 설계와 같은 구조(형식 의무는 템플릿/기계, 내용은 리뷰)다.
  관측된 실패 양상: 그 절이 "None."류 한 줄로 채워지는 **의례화**. 이 설계의 대응이
  정확히 그 지점을 겨눈다 — ⑴ 불요에도 사유 강제(빈 칸 불가·괄호 내용 기계 검사)
  ⑵ 검수 항목 2가 사유 타당성 심사를 명시 ⑶ 인접 도메인 계약을 조사 지시문 상수로.
- **PR 템플릿 체크리스트·DCO·commitlint 류** — "형식만 기계, 내용은 리뷰" 게이트군.
  형식 게이트는 잊힘을 막고 진실성은 리뷰 몫이라는 이 설계의 층 분리(ADR-0013 ④ 계승)와
  동형. 체크박스 피로(기계가 강제하는 형식이 의례가 되는 현상)의 관측이 8절 공시("지어낸
  표명은 기계가 못 잡는다")와 짝이다.

**한계 공시:** 이 검토의 출처는 검수 라운드 2 [cc] 의 제시와 작성자의 오프라인 지식이다 —
research-collector 를 통한 웹 재수집·재검증은 하지 않았다(이 설계 자신이 규정하는 절차의
축소 적용. 표명의 `실패` 가 아니라 `조사함` 인 이유는 검토가 실제로 이뤄졌고 본문에
반영됐기 때문이며, 출처의 신선도 한계를 이 절이 공시한다).
