# 사용법 — 하네스 템플릿

## 0. 전제 (전역 1회 설치, 템플릿은 참조만)

| 의존 | 위치 | 없으면 |
|---|---|---|
| ECC 룰 | `~/.claude/rules/ecc/` | 코딩/테스트 표준 미적용 (하네스는 동작) |
| **ECC 에이전트** (planner·architect·code-reviewer·security-reviewer·pr-test-analyzer) | ECC 플러그인(`ecc:` 접두) 또는 `~/.claude/agents/` 전역 설치본 | 설계·계획·검수·보안검수 4역할 dispatch 실패 → 오케스트레이터가 직접 대체 수행하며 "ECC 미설치" 명시 |
| superpowers 플러그인 | 플러그인 매니저 | 에이전트의 방법론 스킬 호출 실패 → 해당 단계 품질 저하 |
| claude-mem 플러그인 | 플러그인 매니저 | 착수 전 과거 기억 검색(recall) 생략됨 |

| codex CLI (선택) | `npm i -g @openai/codex` + `codex login`(사용자 직접) + `claude mcp add --scope user codex -- codex mcp-server` | 모든 검증 게이트(계획검증·검수·PR점검)의 듀얼 리뷰(cc/cx) 생략 — Claude 단독으로 진행하되 보고에 "듀얼 리뷰 생략" 명시. 이때 Phase 3 의 **싱글턴 CRITICAL/HIGH 교차 검증도 미발동**(반대 진영이 없으므로 트리거의 전건이 거짓) — 보고에 함께 명시 |
| `gh` CLI | PATH | PR 단계(Phase 4) 불가 |

## 1. 설치 (프로젝트당 1회)

```bash
cd ~/.claude/harness-template
./install.sh /path/to/project [프로젝트이름]
```

install이 하는 일: 글루 복사(자체 에이전트 8·스킬 2(harness-orchestrator·readable-writing)·훅 4·제0원칙) + 슬롯 스캐폴드(없을 때만) + settings.json 병합(기존 훅 보존·명령 단위 추가·백업) + CLAUDE.md 포인터 append.

설계·계획·검수·보안검수 4역할은 자체 에이전트가 아니라 **ECC 참조**(`ecc:architect`·`ecc:planner`·`ecc:code-reviewer`·`ecc:security-reviewer`)다 — 하네스 계약(판정 형식·태그·프로필 준수)은 오케스트레이터의 dispatch 계약이 프롬프트로 주입한다. 이 중 2종은 **조건부**로만 돈다: `ecc:architect`(구조적 변경 — 새 모듈/레이어·경계/데이터모델 변경·3개+ 모듈 영향 — 일 때 Phase 2 전단, plan-reviewer가 설계·계획 2-pass 검증), `ecc:security-reviewer`(보안 민감 변경 — 인증/입력/DB/파일시스템/외부API/암호화/결제/시크릿 — 일 때 Phase 3에서 검수와 병렬, CRITICAL=병합 차단). 추가로 테스트가 핵심 방어선인 변경에는 ECC의 `pr-test-analyzer`를 참조 dispatch(`[tq]` 태그) — 템플릿 소유 에이전트가 아니라 전역 ECC 재사용.

**설치 후 반드시 2개 슬롯 채우기:**
1. `.claude/harness/project-profile.md` — §1~§8 (도메인 전부: 스택·검증 명령·불변식·경계면·운영·vcs·예시). 작성 예시는 이 repo의 `examples/chat-system.profile.md`.
2. `.claude/harness/harness.env` — `HARNESS_TYPECHECK_CMD` (Stop 훅이 실행할 타입체크 한 줄. 비우면 타입체크 생략) · `HARNESS_KNOWLEDGE_GATE` (지식 저장소 반영 게이트. **기본 켜짐**이고, 끄는 방법은 **값을 비우는 것 하나뿐**이다 — `"off"`라고 적으면 비어 있지 않으므로 켜진 것으로 읽힌다).
   선택 키 `HARNESS_EXTRA_GATE_DIRS` 는 세션 루트 밖 **다른 git 저장소**들을
   담은 폴더 **하나**(목록이 아니다)를 추가 관할 폴더로 선언하는 옵트인 키다 —
   줄이 없으면(harness.env 를 정상으로 읽을 수 있을 때) 예전 동작 그대로다(5절
   "추가 관할 폴더 슬롯").

**`harness.env` 는 실행되지 않는다.** 확장자와 문법은 셸이지만 훅은 이 파일을 source 하지 않고 줄을 읽어 값만 뽑는다 — 1비트를 얻으려고 사용자 소유 셸 파일에 훅의 제어 흐름을 넘길 이유가 없기 때문이다(`exit 0` 한 줄로 완료 게이트 4종이 흔적 없이 사라진 실측이 있다). 대신 지원 문법이 좁다: **한 키는 정확히 한 번만**, 선언은 줄 **맨 앞**에서 시작, 값에 공백이 있으면 따옴표, 후행 주석은 따옴표 뒤에만. 어기면 그 키는 **미설정**으로 떨어지고 해당 검사가 생략된다(생략 사유는 완료 게이트 메시지에 적힌다). 전체 규칙은 `harness.env` 파일 첫머리에 있다.

**주의: 훅은 세션 시작 시 스냅샷된다** → 설치한 세션에는 발화하지 않고 **다음 세션부터** 적용.

## 2. 무엇이 재사용이고 무엇이 슬롯인가

| 층 | 파일 | 갱신 주체 |
|---|---|---|
| **글루 (재사용)** | `agents/*.md` · `skills/*/`(harness-orchestrator·readable-writing) · `hooks/*.sh` · `harness/principles.md` | `sync.sh` (템플릿 개선 시) |
| **슬롯 (프로젝트 소유)** | `harness/project-profile.md` · `harness/harness.env` | 사용자 — sync가 절대 안 덮음 |
| **참조 (전역)** | ECC 룰 · superpowers 스킬 · claude-mem | 각 시스템 업데이트 시 자동 최신 |

## 3. 일상 사용

- **개발 요청** ("~만들어줘/고쳐줘/추가해줘") → `harness-orchestrator` 스킬이 자동 트리거되어 파이프라인 실행: 질문정리→계획→계획검증→개발→검수→PR→PR점검→변경설명→완료감사. 머지는 항상 사용자 승인 후.
- **부분 재실행** — "검수만 다시", "PR만 다시" → 해당 단계만 돈다.
- **설계 질문** ("왜 이렇게 짰어") → `architecture-guide` 에이전트 직접 호출 (파이프라인 밖).
- **변경 질문** ("이번에 뭐 바뀌었어") → `change-explainer` 직접 호출.

## 4. 템플릿 갱신 (sync)

```bash
cd ~/.claude/harness-template
./sync.sh /path/to/project            # git pull + diff 미리보기 + 글루만 갱신
./sync.sh /path/to/project --no-pull  # 로컬 정본만으로
```

이미 설치된 프로젝트는 sync 전까지 설치 시점 스냅샷 유지(조용한 기본값). 새 설치는 항상 그 시점 최신 글루.

## 5. 강제 훅 게이트 (이 하네스의 무기)

| 훅 | 시점 | 강제 내용 |
|---|---|---|
| guard-master-commit | Bash 실행 전 | master/main 직접 `git commit` 차단 |
| guard-hook-disable | Bash 실행 전 | 에이전트가 `HARNESS_HOOKS`·`ECC_DISABLED_HOOKS`·`ECC_GATEGUARD` 를 끄려 할 때 한 번 세운다. **과속방지턱이지 방벽이 아니다** — 아래 참조. 탈출구가 **없다** |
| guard-codex-invocation | Bash 실행 전 | `codex exec` 호출의 모델(`gpt-6.1-sol`)·effort(`xhigh`) 미달 차단 — 임의 하향 금지 (2026-08-01 사용자 지시 · 2026-09-27 high → xhigh) |
| guard-harness-drift | Bash 실행 전 | 워크트리의 `.claude/harness/` 가 본 저장소와 다르면 차단. 프로필은 planner·architect·reviewer 가 '사실'로 읽는 정본이라, 낡은 사본을 읽으면 **계획·설계가 틀린 전제 위에 짜인다** — PR 게이트로는 못 잡는다(2026-08-21 실사고: 폐기된 계약 위치가 회부 권고안으로 올라감). 캐시 없음. 하네스를 다루는 명령은 통과(데드락 방지) |
| guard-design-path | Skill 성공 후 · 파일 편집 전 | 설계·계획 산출물은 **harness-orchestrator 를 태운 세션에서만** 쓸 수 있다. 그 스킬이 Skill 도구로 실행되면(PostToolUse — 증명 범위는 **지시문 로드까지**이지 파이프라인 완주가 아니다) 세션별 도장(`.harness-path.<cksum>` = `session_id`)을 찍고, `Write`·`Edit`·`MultiEdit`·`NotebookEdit` 로 설계·계획 산출물을 쓰려 할 때 이 세션의 도장이 없으면 차단한다. 스킬 이름은 **정확 일치만**(플러그인 접두 불허 — 임의 네임스페이스 신뢰 구멍). 판정은 좁힌 이름 패턴(한글 문서 유형 토큰 + `.md` · 영문은 번호 앵커·선행·후행 전부 `_`/`-` 경계 필수 + 정확 이름) — **면제 목록이 없고**, 리뷰 명명 계약(`NN_<출처>_…review` 류)·raw·색인·입력서는 패턴 비적중으로 통과하지만 **설계 이름에 리뷰 토큰이 섞이면(`10_설계서_리뷰반영본.md`) 차단된다**. 판독 실패(모듈 로드·JSON 파싱·타입·경로 부재)는 **차단 방향**(fail-closed). 도장은 세션별 파일이라 병렬 세션이 서로 무효화하지 않는다. **하네스 정의 경로는 구조 기반 면제 — 단 실제 설치 루트(프로젝트/.claude·홈/.claude 의 agents|commands|skills, 홈 플러그인 캐시)에 anchor** 된 경로만이며, 판정 전에 **경로를 정준화**한다(realpath — `..`·심볼릭 링크·후행 슬래시·NFD 루트를 전부 해소, r6 듀얼 실측 반영). anchor 없는 글롭(r4)과 문자열 anchor(r5)는 각각 `_workspace/commands/`·`commands/../../` 로 뚫려 폐기됐다. 존재하지 않는 꼬리 경로의 대소문자는 정확 일치 요구(불일치 → 설계 판정으로 낙하, 보수적). 경로 판정 단계 실패는 차단(fail-closed)이고, 설계 이름 판정까지 python 안에서 끝나 셸에는 단일 토큰만 돌아온다(개행 낀 이름은 무조건 차단). **판정은 검사 시점 기준** — 검사 후 심볼릭 링크를 바꿔치는 TOCTOU 는 방벽 밖(공시). 범용 `-plan.md`/`-design.md`(`migration-plan.md` 등)는 산출물(`media-plan.md`)과 이름으로 구분 불가라 **차단 쪽으로 기운다(공시 결정)**. 한글 이름은 **NFC 정규화 후 판정**(macOS NFD 우회 차단). **알려진 한계(공시)**: Bash/PowerShell 리다이렉트·`mv`·파일 쓰기 MCP 도구는 매처 밖 · **직접 슬래시 호출(`/harness-orchestrator`)은 Skill 도구를 우회해 도장이 안 찍힌다**(그 세션의 설계 쓰기가 막히면 Skill 도구 경유로 재호출) · 도장 파일은 모델이 위조 가능 — **과속방지턱이지 방벽이 아니다** |
| check-harness-env | 파일 편집 후 | `harness.env` 편집 직후 알려진 키를 실제 판독기로 읽어, 문법 실수로 **값을 믿을 수 없게 된 키**를 그 자리에서 알린다(안 그러면 해당 검사가 조용히 생략된 채 턴 종료 때에야 드러난다 — ADR-0016). 안 쓰는 키(부재)는 침묵 — 판독기의 rc=1/rc=3 구분이 위양성을 막는다 |
| mark-needs-audit | 파일 편집 후 · Bash 실행 후(성공 `PostToolUse` · Claude Code 가 도구 실패로 처리한 호출의 `PostToolUseFailure` 둘 다 — 실패 쪽이 빠지면 창이 남아 끝난 파일이 다시 플래그에 오른다. 시작조차 안 한 호출(권한 거부·Pre 차단)과 실행 중 사용자 취소의 창은 여전히 남는다. 스윕이 가장 오래된 창을 쓰므로 정상 Bash 를 더 돌려도 잔류 창 수는 줄지 않고, 잔류 창이 있는 동안 모든 Bash 가 앞선 호출의 창 기준으로 스윕해 리뷰 끝난 직전 변경을 다시 플래그한다(지연 오탐이 계속됨 — 60분 만료 정리만 줄인다) — ADR-0024 후속 이력) | 게이트 플래그 5종: `.needs-audit`·`.needs-explain`·`.needs-knowledge`·`.needs-dualreview`·`.needs-retrieval` (코드는 앞 4종 · 설계·계획 산출물은 듀얼리뷰+지식+**머리 표명** · 결정 문서는 지식만). 검사 범위는 아래 "완료 게이트 검사 범위" 참조 |
| verify-before-stop | 턴 종료 시 | 타입체크(`harness.env`) → **혼자 정하지 않았나** → **머리 표명**(설계·계획 산출물 1줄 회수·2줄 레퍼런스 조사 — 형식을 지키면 스스로 풀린다) → codex 듀얼리뷰(추가 관할 폴더 슬롯 항목은 세션 루트가 아니라 그 값의 현재 기록 자리 리뷰로만 풀린다) → change-explainer → **지식 저장소 반영** → **push 미완** → completion-auditor 순서로 미이행 시 종료 차단 (rc=2. 같은 지점에서 진전 없이 3회면 경고와 함께 통과 — 게이트를 하나 지울 때마다 카운터 리셋) |

**지식 저장소 게이트가 아는 것은 계약 하나뿐이다** — "지식 저장소가 설정돼 있으면, 결정·설계가 나온 턴은 반영 없이 끝낼 수 없다." **어디에 어떤 구조로 반영하는지는 하네스가 모른다.** 그건 사용자 층 설정(전역 `CLAUDE.md` 등)이 답하고, 하네스에는 켜짐/꺼짐 1비트만 있다. 그래서 지식 저장소를 바꿔도 하네스는 고치지 않고, 아예 안 쓰는 프로젝트에서도 그대로 돈다.

**탈출구:** `HARNESS_HOOKS=off` (전체) 또는 `ECC_DISABLED_HOOKS`에 `pre:bash:master-guard` / `post:edit:needs-audit` / `post:edit:harness-env`(편집 검증 훅) / `stop:verify`(완료 게이트 전체) / `stop:decision`(결정 게이트만) / `stop:retrieval`(머리 표명 게이트만 — 회수·레퍼런스 두 표명 검사가 **함께** 꺼진다(개별 끄기 없음). **비활성이 "남은 할 일" 판정(`work_pending`)에 접혀 있어, 게이트를 꺼도 남은 플래그가 조기 종료를 막지 않는 유일한 플래그다.** 다른 플래그는 훅 비활성 여부를 각 게이트 호출부에서만 본다) / `stop:dualreview`(듀얼리뷰 게이트만) / `stop:explain`(설명 게이트만) / `stop:knowledge`(지식 게이트만) / `stop:push`(push 게이트만) 나열.

**머리 표명 게이트가 있는 이유 (ADR-0013·ADR-0015):** 설계·계획 산출물(`_workspace/00_design*.md`·`01_plan*.md`)이 저장된 턴은 **머리 두 줄**이 표명 형식을 지키기 전엔 끝나지 않는다. 첫 줄(`사전 결정 회수:`)은 ADR-0009 부터 계약이었는데 검증이 산문("확인한다")뿐이었다 — 산문 절차는 잊힌다(실사고 2회, ADR-0013). 둘째 줄(`레퍼런스 조사: 조사함(<대상·출처>)|불요(<사유>)|실패(<시도 — 사유>)`)은 "조사가 필요한 지시인가"의 판정을 기계가 못 하므로 판정의 **무표명 통과**를 막는 자리다 — 불요·실패에도 괄호 안 사유가 비면 불량이라 조용한 스킵이 없다(ADR-0015. 계기: 인접 도메인 선례 조사가 통째로 생략된 실사고 — "라이브 스트리밍이 아니니 Netflix 는 안 봤다"). **지울 플래그가 없다** — 형식을 지키면 게이트가 스스로 푼다. 형식만 본다: 진짜 읽었는지·조사했는지·표명 내용이 사실인지는 plan-reviewer·codex 검수(산문 계약)의 몫이고, 파일을 지워 우회하는 것도 기계로는 안 막힌다(실존 검증은 감사자 몫). 게이트 ID 는 `stop:retrieval` 그대로다 — **이름이 계약보다 좁다**(회수만 가리키는 이름이 두 표명을 검사한다). 저장소 밖 사용처(셸 설정·CI)에 박힌 ID 라 바꾸지 않았고, 이 괴리는 여기 공시한다. 이 ID 하나로 **두 표명 검사가 함께 꺼진다** — 개별 끄기는 없다.
**`guard-hook-disable` 은 과속방지턱이지 보안 경계가 아니다.** 판정이 정규식 하나라 셸을 해석하지 못한다 — `read`+`export`, 따옴표로 쪼갠 `env 'X''=off'`, 변수 조립, `eval`, 생성한 스크립트 실행은 전부 통과한다(실측). 그럼에도 값을 하는 이유는 막으려는 것이 적대적 공격자가 아니라 **막힌 에이전트의 직진 충동**이고, 그건 `HARNESS_HOOKS=off ...` 라는 직진형으로 나오기 때문이다. 제대로 막으려면 셸 파서가 필요한데, 반쯤 만든 셸 파서는 안 만든 것보다 나쁘다(막힌다고 믿게 하면서 안 막는다 — 이 저장소가 `harness.env` 판독기에서 겪은 늪).

**그래서 위양성 쪽으로 기운다.** 실행 구문과 인용문을 구분하지 않아 `git grep 'HARNESS_HOOKS=off'` 같은 정당한 검색도 막힌다. 의도된 선택이다 — 따옴표 안을 건너뛰면 위양성은 사라지지만 `bash -c 'HARNESS_HOOKS=off ...'` 가 뚫린다. 둘은 문자열로 구별되지 않는 같은 모호성의 양면이고, 위양성은 메시지 한 번이 비용이지만 위음성은 **게이트가 꺼진 걸 아무도 모르는** 것이 비용이다. 차단 메시지가 위양성일 때의 대안(패턴 쪼개기·Write 도구 사용)을 함께 안내한다.

**그리고 환경변수로 끌 수 없다.** 그 탈출구가 있으면 에이전트가 그것으로 이 훅을 끄고 나머지를 전부 끌 수 있어 존재 이유가 사라진다. 사용자가 정말 끄려면 셸에서 직접 `export` 하고 세션을 새로 띄우거나 `settings.json` 배선을 지운다 — 둘 다 사람이 하는 행위다.

**결정 게이트가 있는 이유:** 나머지 게이트는 전부 **산출물**을 본다("코드가 검증됐나", "설명이 나왔나"). 그런데 실측된 실패의 대부분은 산출물이 아니라 **행동**이었다 — 게이트가 막을 때는 세 번 다 따랐으면서, 게이트가 없는 자리에서는 전부 혼자 정하고 보고서에 한 줄 적었다. 그 "한 줄"은 도구 호출이 아니라 문장이라 승인창도 안 뜬다. 그래서 이 게이트만 **대화 기록을 직접 읽는다**: 코드·결정이 바뀐 턴에 결정 표지 어휘를 담은 서술형 문장이 있는데 `AskUserQuestion` 이 0회면 막고, 걸린 문장을 목록으로 보여준다. **질문 한 번이면 풀린다.**

**여기서는 위양성도 위음성만큼 비싸다.** 다른 검사기와 판단이 갈리는 유일한 자리다 — 위양성의 비용이 메시지 한 번이 아니라 사용자에게 가는 **불필요한 질문**이고, 그게 반복되면 질문이 소음이 되어 진짜 질문까지 무시된다. 게다가 이 게이트의 훅·테스트·ADR 이 그 어휘를 데이터로 품어서, 어휘만 보면 **게이트를 유지보수하는 작업 자체가 매번 걸린다.** 그래서 좁힌다: 코드펜스·인라인 코드·인용줄·따옴표 안은 안 보고, 같은 문장에 물음이 있으면 세지 않고, 서술형 단정으로 끝나야 센다. **도구 입력도 안 본다**(발화 텍스트만) — 그 어휘가 적힌 파일을 쓰는 것 자체는 결정이 아니다. 사고 블록과 서브에이전트 발화도 뺀다.

*걸렸는데 결정이 아니라면* 백틱이나 따옴표로 감싸면 빠진다. 그래도 걸리면 사용자에게 알리고 지시를 받는다.

**이건 탐지기가 아니라 과속방지턱이다.** 표지 어휘는 원리에서 유도한 분류법이 아니라 **한 세션에서 실제로 쓰인 문장을 관찰해 뽑은 표본**이다. 그래서:

- 표현을 조금 바꾸면 **빠져나간다**(위음성). 겨누는 것이 적대적 회피가 아니라 무의식적 습관이라 그래도 실효가 남는다
- **영어 발화는 하나도 못 본다.** 표지가 전부 한국어다 — 축 하나가 통째로 비어 있다
- 반대로 그 어휘는 자백에만 나오지도 않는다. `변이 테스트는 별도로 실행됩니다` 같은 **단순 기술 서술도 걸린다.** 어휘에 조건을 덧붙여 좁히지 **않기로 했다** — 그 조건도 같은 출처의 추측이라 문제를 없애는 게 아니라 옮기는 것이기 때문이다
- 목록은 **새는 것을 실제로 본 뒤에만** 늘린다. 이 저장소가 게이트를 만드는 방식 그대로다

**대화 기록을 못 읽으면 막지 않고 통과시킨다 — 이 게이트의 유일한 fail-open 이다.** 기록 형식은 하네스가 소유하지 않아 예고 없이 바뀔 수 있는데, 그때 차단하면 **그 세션 안에 고칠 방법이 없어 통째로 벽돌이 된다**(기록을 고칠 수 없으므로 어떤 행동으로도 안 풀린다). 대신 사유가 마지막 게이트 메시지에 실린다 — 조용히 통과하면 게이트가 죽은 것을 아무도 모른다. **공시된 한계:** `HARNESS_KNOWLEDGE_GATE` 를 비운 환경에서는 결정 문서만 고친 턴이 조기 종료에 걸려 이 게이트까지 오지 않는다(기본값이 켜짐이라 기본 구성에서는 정상 발동). 자세한 근거는 [ADR-0012](decisions/2026-08-10-decision-gate.md).

**push 게이트가 있는 이유:** 이 저장소는 커밋 29개를 잃은 적이 있다. 코드는 다 짜여 있었고 "아직 PR 전이니까"라며 push 를 미뤘다. 게이트는 **네트워크를 쓰지 않는다** — 로컬 remote-tracking ref 만 본다. 원격에 있는데도 ref 가 안 보이면(`remote.origin.fetch` 가 좁혀진 경우) 그 사실을 사유에 적는다. push 여부가 로컬에서 안 보이는 것 자체가 위험이기 때문이다. 예외: guard-codex-invocation은 환경변수 탈출구가 없다 — 변경은 사용자 승인 + 훅·SKILL.md 동시 갱신으로만.

### 완료 게이트 검사 범위 (mark-needs-audit)

판정 **순서가 곧 계약**이다: 개행 가드 → 물리 경로 정규화 → 듀얼리뷰 판정 → 범위 판정 → 분류 → 기록.

- **프로젝트 안** — `_workspace/`·`.claude/`·문서 `*.md`·`*.markdown`(대소문자 무관)는 제외. 나머지는 게이트 4종.
  단 **문서 제외에는 예외가 둘** 있다(동작을 정의하는 마크다운이라 코드로 취급한다):
  `.claude/` 에 앵커된 하네스 경로(`agents/`·`skills/`·`hooks/`·`harness/`·`settings.json`), 그리고
  **프로젝트 자신이 하네스 정본일 때의 `global-agents/*.md`**. 둘 다 `*.md` 제외보다 **먼저** 판정된다.
- **프로젝트 밖 + 하네스 정본 저장소**(루트에 `template/.claude/` 존재) — 저장소 **전체**를 **프로젝트와 같은 규칙으로** 검사한다. `scripts/`·`install.sh`·`global-agents/*.md` 포함(전부 하네스 동작을 정의한다). "같은 규칙"이므로 위의 제외도 **그대로** 적용된다 — 정본 저장소 안이라도 `_workspace/`·`.claude/`·순수 문서는 게이트가 서지 않는다. 지금 읽고 있는 이 파일(`docs/usage.md`)이 그 예다.
- **프로젝트 밖 + 그 외** — `.claude/`에 앵커된 하네스 경로(`agents/`·`skills/`·`hooks/`·`harness/`·`settings.json`)만. **git 저장소가 아니어도** 발화한다.
- **설계·계획 산출물**(`_workspace/[0-9][0-9]_design*.md`·`[0-9][0-9]_plan*.md` — 숫자 두 자리 앵커) — 위치·git 여부와 무관하게 **듀얼리뷰 + 지식 + 머리 표명**(회수·레퍼런스 조사) 플래그를 세운다. 설계가 나온 턴을 반영 없이 끝내면 "왜 그렇게 정했나"가 그 자리에서 사라지고, 그 근거가 정확히 이 파일들이다. 이름·경로에 `codex` 가 들어도 예외가 아니다 — 리뷰 산출물과의 재귀는 명명 계약(리뷰 산출물은 `NN_design`·`NN_plan` 앵커 금지)이 막는다.
- **결정 문서**(`docs/decisions/*.md`) — 문서 제외의 **예외**로 **지식** 플래그만 세운다. 코드가 아니므로 타입체크·변경설명·감사는 과하다. **공시된 한계:** 결정 문서를 이 경로 밖에 두면 게이트가 서지 않는다 — 하네스는 자기가 아는 경로만 알 수 있다.
- **추가 관할 폴더(옵트인 — `HARNESS_EXTRA_GATE_DIRS`)** — harness.env 에 적은
  폴더 하나(슬롯) 안에서, 세션 루트 밖이고 git 최상위가 슬롯 안인 저장소의
  편집은 **그 저장소를 기준으로 프로젝트와 같은 규칙**으로 검사해 게이트 4종을
  세운다. 슬롯 안 `_workspace/`·`_workspace_<이름>/` 의 설계·계획 산출물에는
  듀얼리뷰 + 지식 + 머리 표명을 세운다. 듀얼리뷰는 그 값의 **리뷰 자리**(그
  저장소의 `_workspace/` 또는 옆 `_workspace_<저장소>/`, 설계물은 그 폴더)에서만
  풀린다. 키가 없으면 이 범위는 없다. 쓰는 법과 한계는 아래 "추가 관할 폴더
  슬롯".
- **밖 편집은 절대경로로 기록**한다. 상대경로로 적으면 프로젝트와 외부 저장소가 `README.md` 같은 흔한 경로를 공유할 때 감사자가 프로젝트 쪽 동명 파일을 보고 통과시킨다.
- 플래그를 못 쓰거나 경로에 개행이 있으면 **차단하지 않고** `systemMessage`로 알린다(PostToolUse는 항상 exit 0). git 호출이 실패했는데 조상에 `.git`이 있으면 그 사실도 알린다 — 정본 저장소가 조용히 앵커 전용으로 강등되는 것을 사람이 알 수 있게.

계약의 **기계 정본**은 `tests/mark-needs-audit.cases.sh`의 판정 표이고, 케이스 수는 같은 파일의 `EXPECTED_CASES`가 강제한다. CI가 PR마다 돌린다.

#### 추가 관할 폴더 슬롯 (`HARNESS_EXTRA_GATE_DIRS`)

세션 루트 밖 **다른 저장소**의 편집에도 게이트를 세우는 옵트인 키다. 위 범위
규칙만으로는 세션 루트 밖 저장소(예: 상류 프로젝트에 기여하는 clone 들)를 고쳐도
게이트가 하나도 서지 않는다 — 하네스 정본도 `.claude/` 앵커도 아니기 때문이다.
하네스는 저장소를 위치로 추측하지 않고, 사용자가 harness.env 에 선언한 폴더
하나(슬롯)만 넓힌다. 결정 근거 · 대안 · 전체 공시는
[ADR-0026](decisions/2026-10-14-extra-gate-dirs.md).

**켜는 법**

1.  sync 로 이 판을 받는다. 이미 설치된 프로젝트의 harness.env 에는 이 키도 설명
    주석도 들어가지 않는다(install 은 harness.env 가 없을 때만 만들고, sync 는
    이 키를 더하지 않는다). 설명 주석의 정본은 템플릿의 `harness.env.template`
    이다.
2.  저장소들과 그 옆 `_workspace_<저장소>/` 를 **함께 담은** 폴더 하나를 한 줄로
    적는다: `HARNESS_EXTRA_GATE_DIRS="~/work/tracks"`. 절대경로나 `~/` 로
    시작하고 있는 폴더여야 한다. `:`(목록) · `/` · `~사용자` · `$HOME/…` 은 쓸
    수 없다. clone 하나만 적으면 옆 작업 공간이 폴더 밖이라 설계 산출물 게이트가
    서지 않는다.
3.  편집 검증 훅(check-harness-env)이 침묵하면 정상이다. 값이 틀렸거나
    harness.env 를 믿을 수 없으면 그 자리에서 사유를 알리고, 완료 게이트 훅도
    세션마다 같은 사유당 한 번 알린다 — 고칠 때까지 슬롯은 꺼진다.
4.  키는 그 세션에도 곧바로 적용된다(훅이 호출마다 harness.env 를 읽는다). 켜기
    전에 플래그에 오른 슬롯 안 절대경로 항목은 리뷰 자리 기록이 없어 턴 종료에서
    막힌다 — 그 파일을 다시 저장하면 기록된다. 다만 기록할 수 없는 값(아래
    한계의 "기록할 수 없는 값")은 다시 저장해도 기록되지 않는다.

**리뷰를 두는 곳**

*   리뷰 파일 이름에 `codex` 가 들어가야 한다(`*codex*.md`). 이름 규약은 이것
    하나다.
*   슬롯 저장소 편집의 리뷰는 **그 저장소의 리뷰 자리**에 둔다 — 저장소 안
    `_workspace/` 또는 옆 `_workspace_<저장소>/`. 설계 · 계획 산출물은 그
    산출물이 있는 폴더가 리뷰 자리다. **세션 루트 `_workspace/` 의 리뷰로는
    풀리지 않는다.**
*   저장소(트랙)마다 그 자리에 리뷰를 하나씩 둔다. 한 턴에 저장소 둘을 고쳤으면
    두 곳 모두에 둔다. 자리가 여럿이면 한 번에 모두 저장한다 — 자리 하나씩
    저장하며 Stop 을 되풀이하면 진전으로 세지 않아 같은 지점 차단으로 센다.
*   **모든 리뷰는 마지막 편집 뒤에** 쓴다. 리뷰는 듀얼리뷰 플래그보다 새로워야
    하고, 편집 하나가 플래그를 새로 쓴다.
*   쌍이 아닌 형제 clone 을 상대경로로 고치면(cwd 가 clone A 인데 `../B/x.go`)
    Bash 스윕이 못 잡는다 — 절대경로를 쓰거나 그 clone 을 cwd 로 삼는다. Edit ·
    Write 는 경로 표기와 무관하게 잡는다.
*   옛 설계서를 고치면 머리 표명 게이트도 선다. cwd 가 clone 이면 Bash 마다
    미커밋 삭제를 다시 판정해 플래그를 새로 쓰므로, 끝낸 리뷰가 낡을 수 있다.

**막혔을 때 — 안내의 사유와 출구**

Stop 막음 안내는 리뷰를 기다리는 자리와 현재 리뷰 자리 기록이 없는 값을
나열하고, 아래 사유를 덧붙인다. 사유가 없고 기다리는 자리가 세션 루트
`_workspace` 하나뿐이면 예전 막음 안내가 그대로 나온다.

| 안내의 사유 | 뜻 | 출구 |
|---|---|---|
| (사유 없이 자리 목록만) | 그 자리에 플래그보다 새 `*codex*.md` 가 없다 | 그 자리에 리뷰를 저장한다 |
| "현재 리뷰 자리 기록이 없다" — 슬롯 켜짐 | 기록 실패 · 슬롯 안 `.claude/` 앵커 저장소의 git 판독 실패 · 키를 켜기 전에 오른 항목 | 세션 폴더 쓰기와 그 저장소의 git 판독을 고친 뒤 그 파일을 다시 저장한다 |
| 같은 사유인데 그 값의 기록 줄이 1023바이트를 넘음 | 기록할 수 없는 값(영구) | 다시 저장 · 저장소 이동으로는 이번 막음이 풀리지 않는다 — 사용자 판단 |
| "현재 리뷰 자리 기록이 없다" — 슬롯 꺼짐 | 슬롯을 쓸 수 없는 동안은 저장해도 기록되지 않는다 | 슬롯 값이 검증에 실패했으면 harness.env 슬롯 설정을, harness.env 를 믿고 읽을 수 없으면(슬롯 키든 다른 키든 문법이 깨짐) 그 파일을 정상으로 읽을 수 있게 고친 뒤 다시 저장한다. 그 값의 기록 줄이 1023바이트를 넘으면 다시 저장해도 기록되지 않고, 다음 Stop 이 위 1023바이트 행의 안내(영구)를 낸다 |
| "경로에 제어문자(US)가 있어" | 기록할 수 없는 값(영구) | 다시 저장 · 이름 바꾸기로는 풀리지 않는다 — 사용자 판단 |
| "리뷰 자리 기록 파일을 쓰거나 읽을 수 없다" | 세션 폴더의 `.review-dirs` 가 일반 파일이 아니거나 읽기 · 쓰기 권한이 없다 | 읽고 쓸 수 있는 일반 파일로 고친 뒤 고친 파일들을 다시 저장한다 |
| "세션 루트 경로에 개행이나 제어문자(US)가 있어" | 세션 루트 이름 때문에 판정할 수 없다 | 사용자 판단. 키 줄을 지우거나 값을 비우면 세션 루트 리뷰로 풀린다(harness.env 를 정상으로 읽을 수 있을 때만 — 다른 키가 손상됐으면 그것부터 고친다) — 값만 틀리게 바꾸면 그대로 막힌다 |
| "추가 관할 폴더 모듈을 읽지 못해" · "리뷰 자리 판정이 실패했다(모듈 오류)" | 모듈 유실 · 오류 | 하네스를 다시 설치(sync)한다 |
| "리뷰 자리 판정이 실패했다(환경 장애 …)" | 판정기 awk 가 돌지 못했거나 판정용 임시 파일을 만들지 못했다(awk 없음 · 파일 권한 · 디스크 공간 · 자원 한도 — 셸이 신호로 죽은 경우는 아래 행) | 다시 설치로는 풀리지 않는다 — 사용자 판단. 장애가 걷히면 다음 Stop 이 다시 판정한다 |
| "리뷰 자리 판정이 신호로 끝났다(rc …)" | 평가 서브셸이 신호로 죽었다(rc 128 이상) — 자원 한도(파일 크기 · 메모리)가 셸을 죽였거나 모듈이 바뀌었거나 망가졌다. Stop 은 원인을 가리지 못한다 | 사용자 판단. 모듈 탓이면 다시 설치(sync)로 풀리고, 환경 탓이면 다시 설치로 풀리지 않는다. 원인이 걷히면 다음 Stop 이 다시 판정한다 |
| "슬롯 폴더를 알 수 없어" | 기록 없는 절대경로 항목을 세션 루트 규칙으로 봤다는 알림 — 막는 사유가 아니다 | — |

모든 막음에 공통인 출구도 있다. 같은 지점에서 진전 없이 3회 막히면 경고와 함께
통과한다 — 이때 게이트 플래그 5종이 함께 지워지므로 그 턴의 완료 주장은 믿지
않는다. 사용자 전용 탈출구(`ECC_DISABLED_HOOKS=stop:dualreview` 등)는 그대로다.
키 줄을 지우거나 값을 비우는 것(키 없음)도 사용자 판단이다 — 그러면 기록된 슬롯
의무도 세션 루트 리뷰로 풀린다. 단 harness.env 를 정상으로 읽을 수 있을 때만이다 —
다른 키가 손상됐으면 기록 파일이 있는 한 기록으로 판정하므로 그것부터 고친다. 값만
틀리게 바꾸는 것("슬롯 꺼짐")은 이 출구가 아니다.

**한계 — 못 막는 것은 못 막는다고 쓴다(ADR-0011)**

*관할 범위*

*   **관할 단위 밖:** 저장소의 하위 폴더만 적은 슬롯(최상위가 슬롯 밖) · 슬롯 안
    심링크가 가리키는 바깥 저장소 · 슬롯 밖에 둔 링크 워크트리는 잡지 않는다.
    `/` 는 쓸 수 없는 값이다.
*   **슬롯이 clone 하나면** 옆 `_workspace_<clone>/` 이 슬롯 밖이라 그 설계 ·
    계획 산출물에 게이트가 서지 않는다. 그 폴더는 여전히 리뷰 자리로 기록돼,
    사용자가 선언하지 않은 폴더의 리뷰가 해제에 인정된다 — 짝 이름 하나로
    정해지는 폴더다.
*   **슬롯 안 git 밖 파일**은 게이트가 없다. 설계 모양과 기존 `.claude/` 앵커만
    예외다.
*   **슬롯 저장소 검사는 플래그 4종뿐이다** — 타입체크 · 스타일 · push 확인 ·
    기본 브랜치 커밋 가드가 없다.
*   **세션 루트와의 관계(PR #50 대조):** 세션 루트는 그대로 하나다 — 그 세션의
    첫 훅 호출이 정해 `.root` 에 고정한다. 슬롯은 세션 루트를 바꾸지 않고, 슬롯
    항목의 듀얼리뷰 해제 자리와 발행 게이트 ② 의 리뷰 탐색 자리만 넓힌다. push ·
    타입체크 · 스타일은 PR #50 의 공시대로 세션 루트에서만 본다. 같은 저장소의
    다른 체크아웃 판정이 슬롯 판정보다 먼저이고, 그 체크아웃이 슬롯 안이면 리뷰
    자리는 그 체크아웃의 `_workspace/` · 옆 `_workspace_<이름>/` 이다. 세션
    루트가 슬롯 안 저장소 자신이면 그 저장소 편집은 세션 루트 안 판정(상대경로 ·
    세션 루트 리뷰)이다.
*   **산문으로 남는 것:** NotebookEdit 은 잡지 않는다(기존). 이미 설치된
    프로젝트는 키 한 줄을 손으로 넣는다. 지식 저장소 폴더는 슬롯에 적지 않는다.
    슬롯 저장소의 PR URL · 완료 주장을 변경 설명 · 완료 감사의 입력에 넣는 것은
    오케스트레이터의 산문 계약이고 기계 검증이 없다.

*잡는 쪽 — Bash 스윕* (Edit · Write · MultiEdit 은 아래 꼴도 잡는다)

*   **못 잡는 꼴:**
    *   쌍이 아닌 형제 저장소를 가리키는 상대경로 — cwd 가 clone A 일 때
        `../B/x.go` · `../_workspace_B/02_plan.md`, cwd 가 `_workspace_A` 일 때
        `../B/…`(쌍 = 저장소 T 와 옆 `_workspace_T`).
    *   cwd 가 슬롯 루트일 때의 상대경로(`T/src/x.go`).
    *   저장소만 가리키는 명령에서 무시 폴더(`.git` · `node_modules` · `.venv` ·
        `__pycache__`) 아래의 작업 공간.
    *   작업 공간 안 더 깊은 `_workspace*` — 작업 공간은 한 단계만 훑는다.
        명령이 그 폴더를 직접 가리키면 잡는다.
    *   링크 뒤의 슬롯 작업 공간(`R/wl → 슬롯/_workspace_T`)에 쓴 설계물, 파일
        심링크 토큰(`R/x.go → T/src/x.go` — 슬롯 이전부터 같다).
    *   목록을 읽을 수 없는 작업 공간(find 오류) — 무기록 · 무알림.
    *   슬롯 이름이 `_workspace*` 일 때 `cat > <슬롯>/00_design.md`.
    *   세션 루트가 슬롯 저장소 T 자신일 때 `../_workspace_T/` 에 쓴 설계물 —
        무알림.
    *   홈 토큰(명령문에서 단어 머리가 `~/` 인 경로)으로 읽지 않는 꼴: 중괄호
        확장 `{~/a,~/b}` 안의 경로, 폴더 이름에 `:` 가 든 저장소(토큰이 `:` 에서
        끊긴다 — 절대경로 토큰도 슬롯 이전부터 같다).
    *   변수 · 스크립트 안의 경로, 공백이 든 경로, mtime 을 보존하는 쓰기, 창
        없는 Bash · 취소 · 백그라운드(기존 — ADR-0024), 세션 루트 `_workspace/`
        를 무시하는 프로젝트의 Bash 설계물(기존).
    *   서브에이전트의 cwd 는 미확인이다.
*   **과하게 잡는 꼴**(게이트가 설 뿐 막지는 않는다):
    *   cwd 가 트랙 clone 이면 `git pull` · `rebase` · `switch` · `stash pop` ·
        `git clone` · 압축 해제로 바뀐 추적 파일 전부에 게이트가 선다. Bash 마다
        미커밋 삭제를 다시 판정한다.
    *   `..` 를 지나는 토큰(`~/S/_workspace_U/../T/…`)이 다른 트랙의 작업 공간과
        그 쌍을 뿌리(스윕이 훑기 시작하는 폴더)로 삼는다 — 슬롯 밖으로는 새지
        않는다.
    *   `..` 와 없는 폴더가 섞인 편집 경로가 슬롯 밖 파일을 슬롯 저장소 의무로
        잡을 수 있다(드물다).
    *   슬롯 자신이 git 최상위이고 다른 clone 이 그 안에 중첩되면 슬롯 전체가
        스윕 뿌리가 된다.
    *   `=` 뒤의 `~` 는 왼쪽이 식별자가 아니어도 단어 머리로 읽는다 — 그 이름의
        사용자가 실제로 있을 때만 "일부만 훑었다"고 알리고, 사용자 조회가
        실패하면 있다고 보고 알린다.
*   **상한:** 명령문 경로에서 얻는 뿌리는 3개까지다. 넘거나 홈 토큰을 펼치지
    못하면 일부만 훑었다고 알린다.

*시간 · 비용*

*   **키를 켜면 시간 예산(20 s)과 뿌리 수집 절단이 키가 없을 때부터 훑던 모든
    뿌리에 걸린다** — 세션 루트 · 같은 저장소의 다른 체크아웃 · 명령문 절대경로
    저장소(하네스 정본 clone 포함). 키가 없으면 예산이 없다. 부하가 큰 기기에서
    Bash 하나가 세션 루트 파일 수백 개를 바꾸면 20 s 에서 끊고 알린다 —
    나머지에는 게이트가 서지 않는다. 뿌리 수집 단계에서 끊기면 바꾼 파일이
    하나여도 기록 0 이다(알림은 나간다).
*   **예산이 못 끊는 구간:** 뿌리마다 find 순회 하나와 `git status` 1회, 홈 토큰
    추출과 사용자 조회(`~단어` 수에 이차 비용, 조회 지연). 환경에서 물려받은
    `SECONDS` 는 곧바로 절단된다(알림).
*   **비용:** 링크를 거친 명령문 토큰은 토큰마다 git 을 조회한다(1000개 약
    7.5–8.9 s, 3000개면 시간 절단 알림). 홈 토큰(`~/…`) 수집에는 캐시가
    없다(같은 저장소 1000개 약 14 s, 2000개면 시간 절단 알림). 둘 다 알림이
    나간다.
*   **과알림:** 설계물이 약 194개를 넘으면 먼저 도는 작업 공간 판정이 판정
    상한(200)을 먹어 절단 알림이 과하게 남는다(막는 쪽).
*   **Stop · 발행:** 미충족 5000개 판정 약 1.1–1.9 s, 기록 10000줄에서 막음
    1.63 s · 해제 1.18 s(macOS bash 3.2 실측). 발행 게이트 ② 는 리뷰 자리 수 ×
    자리의 파일 수만큼 본다.
*   **기록 파일 `.review-dirs` 는 덧붙이기만 해서 커진다** — 판정당 2줄, 약
    288 B(추정 — 경로 길이에 비례).

*푸는 쪽 — 리뷰 자리와 수명*

*   **슬롯 항목은 현재 기록 자리로만 풀린다.** 세션 루트 리뷰는 인정하지 않고,
    자리마다 리뷰가 필요하다. 자리는 폴더라서 같은 자리에 다른 세션이 둔
    리뷰로도 풀린다. 다시 고치지 않은 값은 그 편집이 일어난 옛 소속 자리로 푼다.
*   **해제 실패가 넓어진다:** 잔류 Bash 창(ADR-0024 후속 이력)과 창 없이 도는
    미커밋 삭제 재판정이 플래그를 다시 쓰면, 그 전의 모든 자리 리뷰가 낡는다.
*   **기록 실패의 방향** — 한 판정은 ① 갱신 표시(그 값의 기록을 새로 쓰기
    시작했다는 줄 — 끝줄로 남으면 현재 기록이 없다는 뜻) → ② 듀얼리뷰 플래그
    갱신 → ③ 현재 기록을 이 순서로 쓴다. 저장 때 "리뷰 자리 기록에 실패했다 …
    그 전까지 그 값은 턴 종료에서 막히거나 옛 소속 자리 리뷰로 풀릴 수 있다"
    알림이 나가면 원인(세션 폴더 쓰기 · 기록 파일 종류)을 고친 뒤 그 파일을 다시
    저장한다.
    *   ① 만 실패하고 ③ 이 성공하면 정상이다.
    *   ③ 만 실패하면(② 가 실패해도) 끝줄이 갱신 표시라 Stop 이 막는다. 회복
        가능한 원인(일시 쓰기 실패 · 권한 · 파일 종류 · git 판독)을 고친 뒤 다시
        저장하면 missing-record 가 해소되고, 그 뒤 기록 자리 리뷰로 풀린다. 영구
        실패 — 갱신 표시는 1023바이트 안이지만 현재 기록 줄(값과 자리 경로들)만
        넘는 값 — 은 다시 저장해도 같은 제한으로 ③ 이 실패해 풀리지 않는다(아래
        "기록할 수 없는 값").
    *   ①·③ 이 둘 다 일시 장애로 실패하고 Stop 전에 회복되면 옛 줄이 현재로 남아
        옛 소속 자리 리뷰로 풀릴 수 있다. 지속 장애 가운데 권한 · 파일 종류는
        "리뷰 자리 기록 파일을 쓰거나 읽을 수 없다"로 막힌다. 공간 부족은 쓰기
        가능 검사를 통과하므로 일시 장애와 같은 틈이다 — 세션 폴더와 리뷰 자리가
        같은 파일시스템이면 그동안 리뷰 산출물도 쓸 수 없어 해제는 공간이 회복된
        뒤에만 가능하고, 그 저장 때 기록 실패 알림이 나간다.
*   **병렬 판정과 소속 변경:** 같은 값의 두 판정이 병렬로 돌고 그 사이 소속(가장
    안쪽 git 최상위 · 슬롯 범위)이 바뀌면, 늦게 끝난 판정의 현재 기록이 옛 소속
    자리일 수 있다 — kty 수용 2026-10-12(설계 게이트 종결 결정).
*   **슬롯이 꺼진 동안의 갱신:** 슬롯이 꺼진 동안(harness.env 판독 불가 · 값
    불량)의 판정이 같은 값의 플래그를 갱신하면(예: `T/_workspace/00_design.md`
    는 기존 설계 글롭이 잡는다) 기록 줄이 늘지 않아 옛 줄이 현재로 남는다.
*   **가운데 줄 찢김:** 앞선 덧붙이기가 개행 없이 잘린 채 다음 줄이 이어 붙으면
    그 줄은 앞 줄에 흡수된다 — 그 값이 옛 소속 자리 리뷰로 풀릴 수 있다(성립
    조건이 길다). 끝이 잘린 줄은 막는다.
*   **기록할 수 없는 값:** 기록 줄이 1023바이트를 넘는 값과 경로에 US(0x1F)가 든
    값은 다시 저장해도 · 이름이나 위치를 바꿔도 이번 막음이 풀리지 않는다 — 옛
    값이 플래그에 남는다. 슬롯 안 `.claude/` 앵커 파일의 저장소를 git 이 읽지
    못하면(소유권 · 권한 · 손상) git 이 고쳐질 때까지 같다. 출구는 사용자 판단 ·
    사용자 전용 탈출구 · 같은 지점 3회 차단 뒤 통과뿐이다. git 판독 실패는
    사용자가 git 을 고친 뒤 다시 저장하면 — 기록할 수 없는 값이 아니면 —
    기록돼 missing-record 가 해소되고, 그 뒤 기록 자리 리뷰로 풀린다. 키 줄을
    지우거나 값을 비우는 것도 사용자 판단이다 — 그러면 세션 루트 리뷰로 풀린다
    (harness.env 를 정상으로 읽을 수 있을 때만 — 다른 키가 손상됐으면 그것부터
    고친다).
    슬롯이 꺼진 동안 막힌 1023바이트 값은 Stop 이 먼저 꺼진 까닭(값 검증 실패 ·
    harness.env 판독 불가)대로 "고친 뒤 다시 저장하라"고 안내하고, 그대로 한
    뒤의 Stop 이 영구라는 안내를 낸다.
*   **세션 루트 경로에 개행 · US** 가 있으면 듀얼리뷰 플래그가 있는 턴마다
    막힌다 — 키에 값이 있으면(값이 틀려도) 기록 파일이 없어도 막고, harness.env
    를 믿고 읽을 수 없으면 기록 파일이 있을 때 막는다.
*   **평가할 수 없을 때 기록 파일이 있으면 막는다:** 모듈이 유실되거나 평가가
    실패하면 세션 루트 항목만 남은 묶음도 막힌다(출구 — 모듈 유실 · 오류는
    sync, 판독기 awk · 임시 파일의 환경 장애는 사용자 판단). 평가가 신호로
    끝나면(rc 128 이상) 원인을 가릴 수 없어 사용자 판단이다 — 모듈 탓이면
    sync 로 풀리고, 자원 한도 같은 환경 탓이면 다시 설치로 풀리지 않는다. 기록
    파일도 없으면(이중 실패) 예전 판정(세션 루트 리뷰)이다.
*   **풀릴 때는 "슬롯 폴더를 알 수 없어" 사유가 나오지 않는다:** 값 검증 실패나
    harness.env 판독 불가 동안 기록 없는 슬롯 절대 항목이 세션 루트 리뷰로
    풀리면 그 사유는 출력되지 않는다 — 사유는 막음 안내에만 실린다(저장 쪽 슬롯
    알림은 먼저 나간다).

*알림 · 설정*

*   **알림은 세션마다 같은 사유당 한 번이다.** 사유가 정상화된 뒤 다시 생기면
    다시 알린다. 세션 번호가 없는 옛 입력은 표식을 공유한다.
*   **키가 없을 때 예전과 다른 출력(의도된 차이):** harness.env 자리가
    이상하거나(폴더 · 끊긴 링크 · 일반 파일 아래), 읽을 수 없거나, 다른 키
    내용이 손상됐으면(안 닫힌 따옴표 · 히어독) 키를 쓰지 않는 설치본도 알린다 —
    슬롯 상태를 알 수 없기 때문이다(kty 결정). stdout 이 닫혔을 때 예전 훅은
    stderr 에 `write error` 를 냈지만 지금은 아무것도 내지 않는다. 히어독 임시
    파일을 만들지 못하면 예전 스윕은 한 파일도 훑지 않았지만(무음 누락) 지금은
    끝까지 훑는다.
*   **저장 때 알림이 모델 문맥에 들어가는지는 미확인이다**(PostToolUse 의
    `systemMessage`). 그래서 Stop 막음 안내가 출구를 다시 말한다.
*   **발행 게이트 ② 가 기록을 읽지 못한 채 세션 루트 리뷰로 통과하면** 알림만
    내고 통과시킨다.
*   **훅 stdout 을 읽는 쪽이 먼저 닫히면** 완료 게이트 훅이 SIGPIPE 로
    죽는다(rc 141 — 슬롯 이전부터 같다). 알림은 다음 호출이 다시 낸다.
*   **보안 LOW(적대 방어 범위 밖):** 기록 덧붙이기는 `.review-dirs` 심링크를
    따라간다(기존 플래그 기록과 같은 부류). `_workspace_..` 같은 폴더 이름의
    `..` 는 정규화하지 않는다. harness.env 를 지운 뒤 다시 쓰는 비원자 저장
    도중의 훅 호출 하나는 키가 없는 것으로 판정할 수 있다.

## 6. 트러블슈팅

- **Stop 훅이 계속 차단** → 차단 메시지의 게이트 순서대로 처리하라: 결정 게이트(`AskUserQuestion` 으로 실제로 묻는다 — 지울 플래그가 없다) → 머리 표명(산출물 1줄에 `사전 결정 회수:`, 2줄에 `레퍼런스 조사: 조사함(…)|불요(…)|실패(…)` — 지키면 스스로 풀린다) → codex 듀얼리뷰(`.needs-dualreview`) → change-explainer(`.needs-explain`) → 지식 저장소 반영(`.needs-knowledge`) → push(`git push`, 지울 플래그 없음) → completion-auditor(`.needs-audit`). 각 작업을 실제로 마친 뒤에만 해당 플래그를 지운다. 게이트를 하나 지울 때마다 차단 예산이 리셋되므로 순서대로 처리하면 소진되지 않는다. 급하면 탈출구 환경변수. 같은 지점에서 진전 없이 3회면 자동 통과(그 턴의 완료 주장은 신뢰 금지).
- **타입체크가 이상하게 실패** → `harness.env`의 명령을 셸에서 직접 실행해 확인. 도구 부재(rc=127)·타임아웃은 차단 안 하고 생략 처리된다. 문법 실수(등호 뒤 공백·중복 선언 등)는 이제 **편집한 그 자리에서** check-harness-env 훅이 경고한다 — 경고가 떴는데 무시하면 그 키의 검사가 조용히 생략된다.
- **superpowers 스킬 호출 실패** → 플러그인 설치/이름 확인: `test-driven-development`·`writing-plans`·`brainstorming`·`requesting-code-review`·`verification-before-completion`·`systematic-debugging`.
- **에이전트가 도메인을 무시** → 프로필 §가 비어 있지 않은지 확인. 오케스트레이터는 빈 §를 "검증 생략"으로 정직 보고한다.

## 7. 하네스 진화

에이전트/스킬 수정·추가는 이 repo(정본)에서 하고 커밋 → 각 프로젝트에 `sync.sh`. 구조 변경이 크면 `harness` 메타 스킬(운영/유지보수 워크플로우)을 사용. 변경 이력은 각 프로젝트 CLAUDE.md의 변경 이력 표에 기록.

### 제0원칙 판정 기준을 고칠 때

판정 기준(`principles.md`의 `rule:core` 블록)은 **단일 정본**이다 — 고치는 곳은
`template/.claude/harness/principles.md` 한 곳뿐이고, 판정자(plan-reviewer·ecc:code-reviewer)에게는
오케스트레이터가 dispatch 시 이 파일 **전문을 프롬프트에 주입**해 전달한다(SKILL.md 주입 규칙 표).
에이전트 정의에 사본을 두지 않는다 — 복제가 없으면 드리프트도 없다.
