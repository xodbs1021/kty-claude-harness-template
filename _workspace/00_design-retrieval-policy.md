## 0. 입력

ADR-0010 이 못박은 공백 4개(트리거·선택·표명·claude-mem 분업)를 닫는다. 사용자 확정 4건(AskUserQuestion, 2026-08-10):

| 물은 것 | 확정 |
|---|---|
| ② 선택을 누가 하나 | **중간안** — 맥락 전달 + 회수 프로토콜 계약화, 선택은 진입점을 읽는 에이전트 판단 |
| ① 트리거 확장 범위 | **clarifier + 결정 시점 + developer 주소만** |
| ③ 표명 형식 검사 기계화 | **Stop 게이트로 기계화** (내용 검증은 층 위반이라 불가 — 형식만) |
| 2순위 배포 가드 | **C안** (변이 락 무조건 거부 + dirty 거부/`--allow-dirty` 옵트인) — 별도 작업 |

## 1. 판정 프레임 — 무엇을 기계로, 무엇을 단순하게

ADR-0012 ⑤·⑥절의 기준을 그대로 쓴다:

> 게이트를 기계로 두는 이유는 판단이 못 미더워서다. 범위를 정교하게 깎는 것은 게이트를 강하게 만들지 않는다 — 버그는 고치고, 정교함은 참는다.

이 설계의 각 결정에 같은 물음을 적용했다 — 지금 없는 것이 **판단의 실패**인가(→ 기계), **범위의 문제**인가(→ 단순하게). 그리고 임의의 숫자·목록을 지어내야 하는 안은 전부 의심하고 기각했다.

**"관측 우선"과 "산문 승격"의 적용 구분** ([cc] M2 반영): 이 저장소에는 겉보기에 충돌하는 규칙이 둘 있다 — *"실제로 새는 것을 본 뒤에만 방어를 늘린다"*(관측 우선)와 *"산문으로만 존재하는 절차는 훅·게이트로 승격하라"*(산문 승격). 구분 기준은 **의무가 이미 있는가**다. 관측 우선은 **새 의무의 신설**에 적용된다(developer 의무 회수가 그 부류 — 의무 자체가 없다). 산문 승격은 **이미 계약인 의무의 집행**에 적용된다(표명 첫 줄은 ADR-0009 가 이미 계약으로 만들었고, 그 검증 절차가 산문("확인한다 — 없으면 되돌린다")으로만 있다). 산문 절차의 불이행은 이 저장소가 반복 실측한 부류다(2026-08-02 볼트 반영 0회 이행 · 2026-08-03 듀얼리뷰 생략). 4-3 의 기계화는 후자다.

서술은 **주소 / 트리거 / 선택**을 갈라서 한다. ADR-0010 이 셋을 섞어 쓴 것이 혼선의 한 원인이었다:

- **주소** — 지식이 어디 있는지. 프로필 9절 경로 하나. **변경 없음** (ADR-0009 확정 유지)
- **트리거** — 언제 읽는지. **이번에 넓힌다** (2절)
- **선택** — 무엇을 읽는지. **프로토콜만 계약화하고 판단은 위임** (3절)

## 2. 결정 ① 트리거 — 어디서 회수를 발동하나

각 후보에 "여기서 회수하면 무엇이 달라지나"와 "토큰 값을 하나"를 적는다.

| 트리거 | 달라지는 것 | 토큰 값을 하나 | 판정 |
|---|---|---|---|
| architect·planner 착수 전 (현행) | 설계·계획이 선행 결정 위에서 시작 | 이미 지불 중 | **유지** |
| **clarifier — 질문 전** | 과거 결정으로 답이 되는 질문이 사용자에게 안 간다. 질문 소음↓ = 결정 게이트의 위양성 비용 논리와 같은 축 | 진입점+파일 몇 개 읽기 < 사용자 질문 1회의 비용 | **채택** |
| **새 결정을 내리는 순간 (ADR 작성 전)** | 같은 결정의 재결정·선행 결정과 모순되는 결정이 작성 전에 걸린다. ADR-0009 가 진단한 병("같은 결정을 매번 다시 내리고 그 재결정이 또 저장된다")을 정확히 겨눈다 | ADR 은 드물다 — 비용 미미, 값 최대 | **채택** |
| **developer — 주소만** | "이 부분 전에 어떻게 정했더라"가 나올 때 갈 곳이 생긴다. 의무 읽기는 아니다 | 주입은 경로 한 줄 — 0에 가깝다 | **채택 (주소만)** |
| developer 착수 전 의무 회수 | — | 계획서가 이미 회수된 지식을 담고 온다. 같은 지식을 층마다 다시 읽으면 토큰만 쓰고 판단은 안 바뀐다 | **기각** (ADR-0009 Alt C 사유 유지) |
| 검수자(reviewer) 회수 | — | 검수 기준은 프로필 §4 불변식이 그 자리다 — 선행 결정 중 검수에 걸릴 것은 §4 로 증류되는 것이 정본 경로 | **기각** |

**developer 의무화를 하지 않는 이유:** "구현 중 회수가 더 잦다"는 관찰은 맞지만, 그 순간이 언제인지는 기계가 못 본다(에이전트의 판단이다). 판단을 기계로 대체할 수 없으면 주소를 주고 습관을 관찰한다 — 실제로 안 읽어서 새는 것을 본 뒤에만 승격한다(관측 우선 — 새 의무 신설이기 때문).

**새 트리거의 표명** ([cc] M1 반영):
- **clarifier**: 출력 프로토콜의 `판정:` 줄 앞에 `사전 결정 회수: <경로|없음(사유)>` 줄을 추가한다. clarifier 산출물은 `_workspace/` 파일이 아니라 응답 본문이므로 **기계 검증 대상이 아니다** — 오케스트레이터의 산문 확인만 있다. 공시.
- **ADR 작성 전**: ADR 본문의 "관련" 절에 선행·관련 결정 인용(또는 `선행 결정 없음`)을 **작성 규칙으로** 요구한다. ADR 첫 줄은 `# ADR-NNNN:` 형식이 이미 계약이라 첫 줄 표명은 요구하지 않는다(형식 충돌 — [cc] 미확인 3의 답). 기계 검증 없음 — pr-reviewer 점검 항목으로만 얹는다. 공시.
- **developer**: 주소만이므로 표명 없음. 공시.
- 결과: **기계 형식 검증의 대상은 여전히 `00_design*`·`01_plan*` 첫 줄뿐이다.** "트리거를 넓혔는데 값을 했나"를 사후 판정할 데이터는 clarifier·ADR 쪽에선 산문 표명뿐이다 — 8절 공시에 포함.

## 3. 결정 ② 선택 — 결정이 100건이면 무엇을 읽나

**중간안: 하네스는 "무엇을 찾는지"를 주고, 선택은 진입점을 읽는 에이전트의 판단에 맡긴다. 대신 회수의 절차를 계약으로 명문화한다.**

### 회수 프로토콜 (dispatch 계약에 들어갈 문장)

```
1. 프로필 9절의 진입점을 읽는다.
2. 진입점이 목차·라우팅이면, 이번 작업(디스패치 프롬프트의 작업 요약)과 관련된
   항목만 따라가 읽는다. 전부 읽지 않는다.
3. 그 너머의 전문 탐색은 진입점 라우팅으로 부족할 때의 최후 수단이다(도구는 예시일 뿐
   규정하지 않는다).
4. 무엇을 읽었고 무엇이 걸리는지를 회수 블록(4절 형식)으로 낸다.
```

### 층 경계 논증 — 이것이 ADR-0006 을 위반하지 않는 이유

판정 기준 ([cx] MEDIUM 반영으로 정련): **① 하네스가 소유하는 공급자-중립 계약인가 ② 구체 바인딩은 사용자 층에서 오는가 ③ 상위 층 구현을 바꿔도 하네스를 수정하지 않는가.** 셋 다 예여야 한다. "공개 포맷 의존은 층 위반이 아니다, 사유화된 배치 의존이 위반이다"라는 이월 문구는 이 기준의 속기다 — 공개 포맷이라도 하네스가 특정 포맷을 고정 파싱하면 ③이 깨져 위반이고, 반대로 사용자가 슬롯에 넣은 사유 경로는 ②를 지나므로 위반이 아니다.

- 프로토콜이 가정하는 것은 "진입점은 진입점이다"뿐이다 — 목차가 다른 파일을 가리킨다는 **의미적 계약**이지 특정 포맷 파싱이 아니다. 볼트의 4종 세트·`decisions/` 구조 같은 구체 이름은 프로토콜에 없다. ①②③ 전부 통과.
- "무엇을 찾는지"는 하네스가 이미 가진 정보다(디스패치 프롬프트의 작업 요약) — 새 결합 없음.
- **하네스가 보장하는 것**: 회수가 시도된다는 것, 절차가 계약이라는 것, 표명 형식이 검증된다는 것(대상 한정 — 4-3). **보장하지 않는 것**: 올바른 파일이 선택된다는 것, 읽은 내용이 옳게 반영된다는 것.
- 전제: 상위 층 CI 가 링크 무결성·인덱스 완전성·canon 포인터를 보장한다. 이 전제와 위 속기 문구는 현재 `_workspace/`(아카이브되는 자리)에만 있으므로 **ADR-0013 본문에 문장으로 못박는다** ([cc] L1).

### 기각한 대안

- **(a) 상위 층 회수 인터페이스("질의 → 경로 목록") 신설** — 상위 층에 새 규약과 유지보수 의무가 생기고, 하네스가 그 규약의 형식을 알아야 하므로 계약 표면이 넓어진다. 결정적으로, 기계 질의가 서려면 frontmatter 스키마가 서야 하는데 실측이 반대다(타입별 스키마 미정의, `status` 59%·`related-projects` 27% 누락 — 상위 층 실측이라 이 저장소에서 재검증 불가, 인계 문서 수치 그대로 인용). 관측 없이 규약을 지어내는 설계 = 임의 목록 부류.
- **(b) 현재 유지(공시만)** — "알아서 읽어라"는 세션마다 다른 절차를 낳는다. 절차의 부재는 판단 문제가 아니라 **계약 부재**라 비용 없이 닫을 수 있는데 안 닫을 이유가 없다.
- **(c) `harness.env` 에 결정 경로 슬롯(구 C안)** — 기각 사유 이월: 볼트 `canon-path` 를 볼트 CI 가 이미 검증하므로 중복이고, 사용자가 패턴 목록을 유지보수하게 만들어 자동화 목적에 역행한다.

## 4. 결정 ③ 표명 — 강제로 올릴 수 있나

**내용의 기계 검증은 층 위반 없이는 불가능하다 — 못 푼다고 적는다** (ADR-0009 Alt D 사유 유지). 대신 세 단계로 올린다:

### 4-1. 표명을 두껍게 (형식 계약)

산출물 첫 줄은 현행 유지(기계 검증 대상):

```
사전 결정 회수: <읽은 경로>          또는          사전 결정 회수: 없음(<사유>)
```

이어서 **회수 블록**(첫 줄 직후, 산문 목록):

```
- 걸리는 선행 결정: <결정 제목 — 이번 작업에 어떻게 걸리는지 한 줄> (0건이면 "걸리는 선행 결정 없음")
```

지어낸 회수는 경로 한 줄보다 목록이 더 큰 거짓말이 되고, 4-2 의 검증 대상이 생긴다.

### 4-2. 내용 검증은 검수 층으로 — 정확한 주장으로 ([cc] H1 반영)

검사 항목 3개: ① 회수 블록이 형식대로 있는가 ② 산출물이 "걸리는 선행 결정"과 모순되는가 ③ 걸린다고 적힌 결정이 설계·계획에 실제로 반영됐는가.

이 3항목을 **두 곳에** 얹는다:
- **plan-reviewer 점검 항목** — 단 plan-reviewer 의 실행 자체는 기계가 강제하지 않는다(오케스트레이터 산문 계약). **"기존 기계 위에 얹는다"고 말할 수 없다** — v1 의 그 주장은 사실 오인이었다.
- **듀얼 리뷰 규칙의 설계·계획 pass codex 프롬프트 계약** — codex 리뷰 산출물은 `stop:dualreview` 게이트가 기계로 요구한다. 3항목을 codex 리뷰 프롬프트에 명시하면, **기계에 연결된 검증 축이 최소 하나** 생긴다(산출물 존재까지가 기계 보장이고, 프롬프트 준수·내용 판정은 LLM 이다 — 공시).

### 4-3. 형식 검증은 Stop 게이트로 (신규 기계 — `stop:retrieval`)

**판정 프레임 적용:** 표명 첫 줄은 ADR-0009 가 만든 **이미 있는 계약**이고, 그 검증이 산문으로만 있다 — 산문 승격 규칙의 적용 대상이다(1절의 구분). `_workspace/00_design*.md`·`01_plan*.md` 는 하네스 소유 산출물이라 층 위반 없음. 임의 숫자·목록 없음.

```
mark-needs-audit(PostToolUse): 00_design*.md·01_plan*.md 저장 시
  → 단, 이름에 codex 가 들어가면 제외 — 검수 산출물 명명 계약(_workspace/*codex*.md)과의
    재귀 충돌 방지. 이 제외는 듀얼리뷰·지식 플래그에도 함께 적용한다(기존 잠복 결함 —
    00_design_codex.md 저장이 듀얼리뷰를 재무장시키는 "검수의 검수" 루프 — 를 같이 닫는다)
  → .needs-retrieval 플래그에 경로 기록 (기록값 계약은 기존과 동일: 안=상대, 밖=절대)

verify-before-stop(Stop): retrieval_gate_active() = 플래그 비어있지 않음 AND !hook_disabled(stop:retrieval)
  — knowledge_gate_active 와 같은 결합 판정. 발효 여부를 이 한 곳에 모은다 ([cc] H5)

  게이트 3.4 (결정 게이트 3.2 뒤 · 듀얼리뷰 3.5 앞):
  retrieval_gate_active 일 때, 플래그의 각 경로에 대해:
    - 경로 해석: 절대경로는 그대로, 상대경로는 $PROJECT_DIR 기준 ([cc·cx] — 미정이면
      다른 cwd 에서 "소실"로 오인돼 조용히 통과한다)
    - 파일 없음 → 그 항목 건너뜀 (한계 공시 — 아래)
    - 파일 있음 → 첫 줄이 "사전 결정 회수:" + 공백 아닌 내용인가.
      빈 파일·읽기 실패·접두어만 있음 → 불량 (fail-closed)
    - 플래그 파일 자체를 읽을 수 없음 → 차단 + 사유 (fail-closed — "검사 대상 0건"으로
      위장되지 않게)
  불량 0건 → 플래그 자동 해제. 해제 후 "남은 할 일"을 재평가해 아무것도 없으면 exit 0
    ([cx] HIGH — 재평가 없이 흘러가면 맨 아래 감사 게이트가 빈 목록으로 허위 차단한다)
  불량 ≥1건 → gate_budget "retrieval" + emit_decision_note 포함 차단 메시지(불량 파일과
    사유 나열) ([cc·cx] — 판독 불가 경고 전파는 ADR-0012 ② 계약이다)

  차단 지문: flags_fp 에 "r:<정렬된 불량 경로 목록>" 을 넣는다 ([cx] HIGH — 존재 비트만
    넣으면 4개 중 1개씩 고치는 실제 진전이 같은 지문으로 세어져 예산이 소진되고, 그때
    다른 플래그 4종까지 전부 삭제된다. push 가 "몇 개 남았나"를 지문에 넣는 것과 같은 논리)
  조기 종료 조건 · 예산 소진 정리 목록(rm + changed 나열) 에 retrieval 플래그 포함 —
    조기 종료는 retrieval_gate_active 로 묻는다(게이트를 끈 환경에서 남은 플래그가
    읽기 전용 턴을 막으면 안 된다 — knowledge 와 같은 부류)
  decision_armed 에 retrieval_gate_active 를 추가한다 ([cc] M3 — 설계·계획 산출물이
    나온 턴은 결정이 나온 턴이다. 기존 4플래그와 같은 성격. 케이스로 고정)
```

- **자동 해제**가 이 게이트의 형태다. 결정 게이트가 "실제로 물으면 풀린다"이듯 이것은 "형식을 지키면 풀린다" — 지울 플래그를 에이전트 손에 주지 않는다.
- **fail-closed 인 이유:** 위양성 비용이 메시지 한 번이다(사용자에게 가는 질문이 아니다) — 집안 표준대로 기운다. 결정 게이트만 예외였던 이유(질문 소음)가 여기 없다.
- **순서(3.4)의 근거:** 표명 없는 산출물로 리뷰(3.5)에 노력을 쓰기 전에 잡는 편이 싸다. 정확성 문제가 아니므로 옮기는 변이로 잰다.
- **파일 소실을 건너뛰는 이유:** 차단하면 산출물을 아카이브한 턴이 벽돌이 된다(고칠 대상이 없다). **이 스킵이 삭제 우회를 연다는 것을 그대로 공시한다** ([cc] H2·[cx] MEDIUM — v1 은 "듀얼리뷰 게이트가 산출물 실존을 요구한다"고 적었는데 사실이 아니다. 듀얼리뷰 게이트는 플래그만 본다(README ⑪). 삭제 우회의 적발은 기계가 아니라 감사자 몫이다).

## 8. 공시된 한계 (ADR Consequences 로 갈 것)

- **읽었다는 것은 여전히 기계가 못 본다.** 형식 게이트는 "표명이 형식대로 있다"까지만.
- **내용 검증의 실행을 기계가 보장하는 축은 codex 리뷰 산출물 존재까지다.** plan-reviewer 실행 자체는 산문 계약이고, codex 프롬프트 준수·내용 판정은 LLM 이다.
- **선택 품질 보장 없음** — 진입점 너머 라우팅과 상위 층 CI 전제(링크 무결성·인덱스 완전성·canon 포인터)에 달렸다. 전제가 깨져도 하네스는 감지하지 못한다.
- **회수 블록을 지어내는 에이전트는 기계로 못 잡는다** — 잡는 것은 검수 층이고, 그것도 확률적이다.
- **삭제 우회는 기계로 안 막힌다.** 파일 소실 항목은 건너뛰고, 듀얼리뷰 게이트는 산출물 실존을 검사하지 않는다(플래그만 본다). 실존 검증은 감사자 몫(README ⑪ 그대로).
- **Write/Edit 도구 밖 생성(`bash cat > …`)은 게이트가 안 선다** — PostToolUse 앵커의 공통 한계(기존 게이트 4종과 동일). 이 게이트는 "형식 검증"을 새로 약속하므로 약속의 경계를 같이 적는다.
- **서브에이전트가 직접 산출물을 저장하는 구성은 미실측이다.** 현 SKILL 은 오케스트레이터가 저장하므로 무관하지만, 서브에이전트의 Write 에 PostToolUse 훅이 발화하는지는 확인하지 않았다 — 그 구성을 도입하려면 먼저 실측해야 한다.
- **clarifier·ADR 트리거의 표명은 산문 검증뿐이다** — 사후 판정 데이터가 약하다. 값을 했는지의 관측은 세션 기록·산출물 표명 줄에 의존한다.
- **결정 문서를 `docs/decisions/` 밖에 두면 지식 게이트가 안 선다**(mark-needs-audit 공시의 이월) — 하네스는 자기가 규정한 경로만 안다. 닫지 않고 공시 유지.
- **developer 의 실제 회수 습관은 관측 대상** — 안 읽어서 새는 실측이 나오면 그때 승격.

## 9. ADR 번호 판단

**ADR-0013 신설 + ADR-0010 은 superseded.** 재작성(proposed→accepted)하지 않는 이유: ADR-0010 의 Decision 은 "정책을 정하지 않는다 — 공백을 못박는다"이고 그 결정은 그 자체로 실행됐다(공백 4개가 이 설계의 입력이 됐다). 내용을 갈아끼우면 "공백이 명시적으로 선언됐던" 이력이 사라진다 — ADR-0006 의 proposed→accepted 는 결정 내용이 동일한 채 이행만 완료된 경우라 성격이 다르다. (검수 [cc] L4 — 번호 0013 비어 있음 확인.)
