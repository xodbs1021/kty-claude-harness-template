> **한 줄:** 어떤 프로젝트든 `install.sh` 한 번 + 프로필 한 파일로, 질문정리→설계→계획→개발→검수→PR→설명→지식 저장소반영→완료감사 파이프라인과 강제 훅·Claude+Codex 듀얼 리뷰를 얻는 재사용 글루 층.

## 1. 이것이 무엇인가

CHZZK/SOOP 채팅 시스템을 만들며 겪은 실제 실패들(§5)로부터 진화한 개발 하네스를, **도메인을 빼고 접착제만 남겨** 어느 프로젝트에나 붙일 수 있게 일반화한 것이다.

```
사용자 요청
   │
   ▼
[clarifier] 모호점·비가역 결정 → 질문 게이트           ─┐
   ▼                                                   │
레퍼런스 조사 판단 → (필요 시)                          │
[research-collector]→[research-evaluator] 주입          │
   ▼                                                   │
[ecc:architect] (구조적 변경만) 설계서                   │ Phase 0에서
   ▼                                                   │ 오케스트레이터가
[plan-reviewer 1차] 설계 검증 ⇄ 루프                    │ 프로필 §섹션을
   ▼                                                   │ 각 에이전트
[ecc:planner] 계획서 → [plan-reviewer 2차] ⇄ 루프       │ 프롬프트에
   ▼                                                   │ 런타임 주입
[developer] TDD 구현 ⇄ [ecc:code-reviewer] 검수         │
   ‖ (보안 트리거 시) [ecc:security-reviewer] 병렬       │
   ▼                                                   │
[pr-author] 브랜치→PR ⇄ [pr-reviewer] 점검              │
   ▼                                                   │
[change-explainer] 사용자용 변경 설명   ← Stop 훅 강제   │
   ▼                                                   │
지식 저장소 반영                              ← Stop 훅 강제   │
   ▼                                                   │
[completion-auditor] 완료 주장 1차 증거 감사 ← Stop 훅 강제
   ▼
머지 (항상 사용자 승인 후)                               ─┘
```

**모든 검증 게이트(계획검증·검수·PR점검)는 Claude+Codex 듀얼**로 돈다 — 같은 산출물을 codex(`gpt-5.6-sol`, effort high 고정)가 병렬 독립 리뷰하고, 지적을 `[cc]`/`[cx]`/`[cc·cx]` 태그로 통합하며, 판정 충돌 시 보류가 이긴다(§3-⑪). codex 미설치·호출 실패 시에는 Claude 단독으로 진행하되 보고에 "듀얼 리뷰 생략"을 명시한다 — 조용한 성공 위장 금지.

파이프라인 밖 상시 자문: **architecture-guide** — "왜 이렇게 짰나"를 결정·대안·트레이드오프로 설명.

## 2. 3층 구조 — 참조 / 글루 / 슬롯

| 층 | 무엇 | 갱신 주체 |
|---|---|---|
| **참조** (복사 안 함, 전역 1회 설치) | ECC 룰(코딩/테스트/보안 표준) · superpowers(방법론 스킬) · claude-mem(세션 기억 자동 캡처+검색) · find-skills(스킬 생태계 검색 — 진화 시 "만들기 전에 찾는다") | 각 시스템이 업데이트되면 모든 프로젝트에서 즉시 최신 |
| **글루** (이 repo 소유, install 시 복사) | 자체 에이전트 8 · 스킬 2(harness-orchestrator·readable-writing) · 강제 훅 4(커밋 가드·codex 규율 가드·게이트 플래그·Stop 게이트) · 제0원칙 (설계·계획·검수·보안검수 4역할은 ECC 에이전트 **참조** — dispatch 계약으로 호출 · 테스트품질 ecc:pr-test-analyzer는 조건부 `[tq]` 참조) | 이 repo에서 개선 → `sync.sh`로 프로젝트에 전파 |
| **전역 글루** (이 repo `global-agents/` 소유, install/sync 시 `~/.claude/agents/`로 배포) | 프로젝트 무관 전역 에이전트 — research-collector(수집 [rc]) · research-evaluator(독립 평가 [re]). 정본이 repo인 이유: 전역 디렉토리는 버전 관리가 안 된다 ([ADR-0002](docs/decisions/2026-07-20-global-agents-layer.md)) | 이 repo에서 개선 → install/sync가 전역 갱신 |
| **슬롯** (프로젝트 소유, 절대 안 덮음) | `project-profile.md`(도메인 전부: 스택·검증·불변식·경계면·운영·vcs·예시) · `harness.env`(타입체크 명령) | 사용자 |

새 프로젝트 온보딩 = 슬롯 한 파일 채우기. 에이전트·훅은 손대지 않는다.

## 3. 왜 이런 구성인가 — 핵심 설계 결정

각 결정을 "결정 / 대안 / 왜"로 기록한다. (architecture-guide가 설명할 때의 근거 원장이기도 하다.)

**① 파이프라인 + 3중 generate-verify 루프 (계획·개발·PR)**
대안: 유능한 에이전트 하나가 다 하기. → 결함은 늦게 잡을수록 비싸다. 계획 결함을 개발 후에 발견하면 코드·검수·PR 전부 재작업. 각 산출물마다 생성자와 다른 검증자를 붙여 가장 싼 지점에서 잡는다. 역할 분리는 컨텍스트 오염도 막는다.

**② 강제력은 훅이 소유한다 — 이 하네스의 무기**
대안: "검수해라, 설명해라"를 산문 지시로. → 실사고(§5)로 증명됐듯 산문은 생략된다. `PreToolUse`(기본 브랜치 커밋 차단 + codex 호출 규율)·`PostToolUse`(게이트 플래그 5종: `.needs-audit`·`.needs-explain`·`.needs-knowledge`·`.needs-dualreview`·`.needs-retrieval`)·`Stop`(타입체크→**혼자 정하지 않았나**→**머리 표명**(회수·레퍼런스 조사)→듀얼리뷰→설명→지식 저장소반영→push 미완→감사 미이행 시 종료 차단)은 모델의 선의와 무관하게 발화한다. 그 중 **결정 게이트만 산출물이 아니라 에이전트의 행동을 본다**(⑬). superpowers가 방법론을 주지만 강제력이 없다 — 훅이 그 빈자리를 채운다. 단 벽돌 방지(같은 지점에서 진전 없이 3회면 경고와 통과 — 게이트를 지울 때마다 카운터 리셋이라 순차 처리로는 소진 안 됨)와 탈출구(`HARNESS_HOOKS=off`, 게이트별 `ECC_DISABLED_HOOKS`)를 항상 남긴다: 강제 장치가 세션을 인질로 잡으면 안 된다. 예외: guard-codex-invocation에는 환경변수 탈출구가 없다 — 변경은 사용자 승인 + 훅·SKILL.md 동시 갱신으로만(⑪).

**③ 단일 프로필 슬롯 + 런타임 주입**
대안 1: 도메인을 각 에이전트에 인라인(원본 방식) → 같은 사실이 5+개 파일에 중복, 바뀌면 드리프트. 대안 2: 에이전트에게 "프로필을 읽어라" 지시만 → 안 읽으면 도메인이 컨텍스트에 아예 없음. → 채택: 도메인은 프로필 한 파일(디스크의 단일 원천), 오케스트레이터가 dispatch마다 해당 §전문을 프롬프트에 동봉(런타임 인라인). **에이전트의 순종에 안 맡긴다.** 읽을지 선택할 기회 자체를 없앴고, 그래도 어기면 같은 프로필을 근거로 한 reviewer가 잡는다.

**④ 제0원칙은 developer가 아니라 하네스가 소유**
"코드는 사람을 위한 것 — 이름=계약, 구현=교체 가능한 부품, 과함도 배신(YAGNI)". 대안: developer 정의에만 넣기. → 모듈 경계는 **계획에서 정해지고 리뷰에서 강제**되므로 developer만 알면 샌다. planner(설계 반영)·plan-reviewer(검증)·developer(구현)·reviewer(적발)·architecture-guide(설명)가 같은 파일(`harness/principles.md`)을 공유한다.

**⑤ ECC·superpowers·claude-mem은 참조, 복사 금지**
대안: 좋은 부분을 템플릿에 복사해 자기완결. → 복사본은 그 순간부터 낡는다(버전 드리프트). 참조는 원본이 업데이트되면 공짜로 최신. superpowers 스킬은 서브에이전트의 `Skill` 도구로 런타임 로드(복사 0), ECC 룰은 세션 상주라 인용만, claude-mem recall은 `claude-mem:mem-search` 스킬 호출로 위임. 전역 `using-superpowers`의 "응답 전 스킬 먼저" 선점만 CLAUDE.md 지시로 꺼서 오케스트레이터가 순서 통제권을 유지한다.

**⑥ per-agent 스킬 붕괴**
원본은 에이전트마다 방법론 스킬이 짝(11개). 해부해 보니 내용물 = 에이전트 정의와 중복(~50%) + 도메인 사실(~40%, →프로필) + 트리거 문구(~10%, →오케스트레이터 description). 남는 알맹이가 없어 통째로 흡수했다. 단독 요청("검수만 다시")은 오케스트레이터 Phase 0의 부분 재실행이 커버.

**⑦ 조건부 전문가 패턴 (ecc:architect · ecc:security-reviewer)**
대안: 모든 변경에 설계·보안 검토. → 자잘한 수정에 매번 설계서를 만들면 과설계 공장이고, 모든 diff에 보안 검수는 소음이다. 오케스트레이터가 **트리거 기준**(구조적: 새 모듈/경계·데이터모델 변경/3+모듈 영향 · 보안: 인증/입력/DB/파일시스템/외부API/암호화/결제/시크릿)으로 판별해 해당할 때만 투입. plan-reviewer는 2-pass(1차 설계만, 2차 계획+정합성) — 호출마다 새 컨텍스트에 단일 임무라 혼란이 없고, 설계↔계획 정합성을 보는 주체가 유지된다.

**⑧ 하이브리드 메모리**
하중지지 사실(규칙·확정 결정·로드맵·프로필)은 파일 메모리(항상 로드), 긴 꼬리(세션 서사)는 claude-mem 자동 캡처+필요 시 검색. 전부 파일이면 비대, 전부 claude-mem이면 매 세션 재검색 위험. 승격 규칙: 검색에서 하중지지 사실이 나오면 파일로 승격.

**⑨ 역할 등가는 참조로, 계약은 dispatch로 (2026-07-20)**
설계(architect)·계획(planner)·검수(code-reviewer)·보안(security-reviewer) 4역할은 ECC에 역할 등가 에이전트가 이미 있어 자체 정의를 삭제하고 참조로 교체했다. 대안: 자체판 유지(계약이 정의에 내장돼 편함). → "만들기 전에 찾는다"를 자기 자신에게도 적용 — 역할 전문성은 ECC가 유지보수하고, 하네스 고유 계약(판정 형식·카테고리 태그·프로필 준수·수정 금지)은 오케스트레이터의 **dispatch 계약**이 프롬프트 주입으로 강제한다(③의 런타임 주입과 같은 원리). 생태계에 등가가 없는 게이트·감사류 5종(clarifier·plan-reviewer·pr-author 포함 8종)만 자체 소유로 남긴다 — 이것이 이 하네스의 차별점이다.

**⑩ 전역 에이전트 층 — 정본=repo, 배포=~/.claude/agents/ (2026-07-20)**
리서치 수집/평가처럼 프로젝트 무관 에이전트는 프로젝트 글루로도, 전역 직접 작성으로도 안 맞는다(전자는 용도 불일치, 후자는 버전 관리 불가). `global-agents/`를 정본으로 install/sync가 전역 배포한다. reporter 에이전트는 기각 — evaluator 분리의 가치는 독립성이지만 보고서의 가치는 사용자 맥락이고 그것은 메인 세션에 있다. 상세: [ADR-0002](docs/decisions/2026-07-20-global-agents-layer.md).

**⑪ 모든 검증 게이트는 이종(異種) 듀얼 — Claude + Codex (2026-08-01 사용자 확정)**
대안: Claude 리뷰어 단독. → 같은 모델은 생성자와 맹점을 공유한다 — 실제로 Claude 단독 검수가 놓친 CRITICAL을 codex가 적발했다(2026-08-03 POK-30). 계획검증·검수·PR점검 전 게이트에 codex를 병렬 투입하고 `[cc]`/`[cx]`/`[cc·cx]` 태그로 통합, 판정 충돌 시 보류 우선. 모델(`gpt-5.6-sol`)·effort(`high`)는 하드코딩 — "작업이 작다/비용" 사유의 임의 하향 실사고(2026-08-01)를 `guard-codex-invocation.sh`(PreToolUse)가 명령 위치의 `codex exec` 호출을 기계 차단한다(커밋 메시지·문서 속 문자열은 오탐 제외). 규정 자체도 기계화했다: 설계·계획 산출물 저장과 코드 편집이 `.needs-dualreview`를 세우고, Stop 훅이 이 플래그가 서 있는 한 종료를 막는다 — 플래그는 codex 리뷰 산출물(`_workspace/*codex*.md`) 저장·`[cc]`/`[cx]` 통합 후에만 지우는 규율이다(훅은 플래그만 보므로 산출물 실존 검증은 감사자 몫) — sync 누락으로 구버전 스킬이 듀얼 리뷰를 조용히 생략한 실사고(2026-08-03)의 재발 방지. 같은 사고에서 오케스트레이터 Phase 0의 정본 드리프트 확인(스킬·훅이 정본과 다르면 작업 전 sync 먼저)도 나왔다.

**⑫ 지식 반영도 완료 조건 — 지식 저장소 게이트 (2026-08-02 사용자 확정)**
대안: "세션 끝나면 어디에든 정리해라" 산문 규칙. → 세션 내내 0회 이행된 실사고. 코드·설정이 바뀐 턴은 **지식 저장소 반영** 또는 불요 사유 기록 없이 종료 불가(`.needs-knowledge` + Stop 훅 `stop:knowledge`). 하네스가 아는 것은 계약 하나뿐이다 — 저장소가 **어디이고 어떤 구조인지는 사용자 층 설정이 답한다**(ADR-0006). completion-auditor가 반영 증거(커밋 해시·파일 실존)를 1차 증거로 검증한다 — 코드가 끝나도 지식이 안 남았으면 완료가 아니다. 게이트는 기본 켜짐이고 `harness.env` 의 `HARNESS_KNOWLEDGE_GATE` 를 비워서만 끈다(ADR-0008).

**⑬ 게이트 하나는 산출물이 아니라 에이전트를 본다 — 결정 게이트 (2026-08-10 사용자 확정)**
대안: 승인 모드에 맡긴다. → **승인창은 *한 일*에만 뜬다.** 안 한 일(묻지 않은 것·push 하지 않은 것)은 원리적으로 안 잡힌다 — 실측에서 다른 훅이 26번 승인을 요구하는 동안 혼자 결정하는 것은 **한 번도** 못 막았다. 완료 게이트 넷이 전부 산출물을 볼 때, 실패는 게이트가 없는 축(물어야 할 결정·push·기록된 선호)에서만 났다. 그래서 Stop 훅이 **이 턴의 대화 기록을 직접 읽어** 판정한다: 코드·결정이 바뀐 턴에 결정 표지 어휘를 담은 서술형 문장이 있는데 `AskUserQuestion` 이 0회면 차단하고 걸린 문장을 보여준다. 질문 한 번이면 풀린다. **여기서만 위양성이 위음성만큼 비싸다** — 불필요한 질문이 반복되면 소음이 되고, 소음이 되면 진짜 질문도 무시되며, 무엇보다 이 게이트의 훅·테스트·ADR 이 그 어휘를 데이터로 품어 **게이트를 유지보수하는 작업 자체가 걸린다.** 그래서 구조적 제외(코드펜스·인용·따옴표)와 서술형 종결 요구로 좁히고, **도구 입력은 아예 안 본다.** 그리고 대화 기록을 못 읽으면 **막지 않고 통과시킨다** — 이 게이트의 유일한 fail-open 이다(형식은 하네스 소유가 아니고, 차단하면 그 세션 안에 고칠 방법이 없다). 대신 사유를 마지막 게이트 메시지에 싣는다. 상세: [ADR-0012](docs/decisions/2026-08-10-decision-gate.md).

**⑭ 지식 회수는 표명이 계약이고, 형식은 기계가 지킨다 — 회수 표명 게이트 (2026-08-10, ADR-0013)**
대안: 회수 표명("산출물 첫 줄 `사전 결정 회수:`")의 검증을 산문으로 둔다. → 산문 절차는 잊힌다(⑫·⑪의 실사고와 같은 부류). 표명 첫 줄은 ADR-0009 부터 **이미 계약**이었으므로 그 집행을 게이트로 승격한다 — 설계·계획 산출물(`_workspace/00_design*.md`·`01_plan*.md`)이 저장된 턴은 첫 줄이 표명 형식을 지키기 전엔 끝나지 않는다(`stop:retrieval`). **지울 플래그가 없다** — 형식을 지키면 게이트가 스스로 푼다(결정 게이트의 "실제로 물으면 풀린다"와 같은 구조). 기계가 보는 것은 **형식뿐**이다: 진짜 읽었는지·회수 블록 내용은 plan-reviewer·codex 검수(산문 계약)의 몫이고, 내용의 기계 검증은 층 위반이라 불가능하다(ADR-0006). 회수의 나머지 — 트리거 4곳(architect·planner 착수 전 / clarifier 질문 전 / ADR 작성 전 / developer 주소) · 선택 위임 프로토콜 · claude-mem 분업 — 은 [ADR-0013](docs/decisions/2026-08-10-knowledge-retrieval-policy-decided.md).

**⑮ 레퍼런스 조사도 표명이 계약이다 — 머리 표명 게이트로 일반화 (2026-08-11, ADR-0015)**
대안 1: "조사가 필요한 지시"를 키워드 목록으로 기계 판정. → 임의 목록 부류(⑬의 어휘 목록과 같은 이유로 기각 — 판정은 기계 불가). 대안 2: 전용 게이트 `stop:reference` 신설. → 회수 게이트가 이미 가진 상태기계 결합 8종(플래그·work_pending·지문·예산 키·자동 해제·재평가·decision_armed·개행 방어)을 정보 이득 없이 다시 걷는다. → 채택: **판정의 무표명 통과만 막는다** — 설계·계획 산출물 **둘째 줄**에 `레퍼런스 조사: 조사함(<대상·출처>)|불요(<사유>)|실패(<시도 — 사유>)` 표명을 의무화하고, 기존 회수 게이트(3.4)를 **머리 표명 게이트**로 일반화해 두 줄을 한 기계로 검사한다(회수 블록은 셋째 줄부터). **불요·실패에도 괄호 안 사유가 비면 불량** — 조용한 스킵 불가화가 핵심이다(계기: 인접 도메인 선례 조사가 통째로 생략된 실사고 — "라이브가 아니니 Netflix 는 안 봤다". 답은 Netflix Live Origin 에 있었다). 조사 실행은 research-collector→research-evaluator(산문 계약), 불요 사유의 타당성·조사 품질 심사는 plan-reviewer·codex 의 레퍼런스 검증 3항목(산문 계약). 상세: [ADR-0015](docs/decisions/2026-08-11-reference-research-gate.md).

## 5. 진화 이력 — 실사고가 만든 설계

이 하네스의 모든 강제 장치는 이론이 아니라 **실제로 겪은 사고**의 흉터다:

| 실사고 | 낳은 설계 |
|---|---|
| "됐다"는데 실제론 안 됨 (커밋 없이 push 보고, 테스트 안 돌리고 통과 주장) | completion-auditor + Stop 훅 감사 게이트 — 주장을 믿지 않고 1차 증거로 |
| 스택 PR의 base 삭제로 뒤 PR이 통째로 닫힘 | 스택 PR 금지, 기능마다 기본 브랜치에서 새 브랜치 + PreToolUse 커밋 가드 |
| 머지됐는데 사용자는 옛 빌드 화면을 보며 "그대로"라고 항의 (2026-07-12) | 프로필 §6 운영 모델 + 감사자의 "머지 ≠ 운영 반영" 판정 의무 |
| 변경 설명 단계를 오케스트레이터가 임의 생략 (2026-07-13) | `.needs-explain` 플래그 + Stop 훅 설명 게이트 — 산문이던 절차를 훅으로 |
| 도메인 지식이 에이전트 5+곳에 산재, 재사용 불가 | 단일 프로필 슬롯 + 런타임 주입 — **이 템플릿의 탄생 이유** |
| 신생 repo에서 커밋 가드가 우연히 통과 (Stage 6a에서 발견) | unborn HEAD 처리 명문화 — 우연을 의도로 (a9cad82) |
| codex 리뷰를 "작업이 작다/비용"이라며 모델·effort 임의 하향 (2026-08-01) | 듀얼 리뷰 규칙에 모델·effort 하드코딩 + guard-codex-invocation 훅 — 미달 호출을 PreToolUse에서 차단 (환경변수 탈출구 없음) |
| 지식 저장소 반영 산문 규칙이 세션 내내 0회 이행 (2026-08-02) | `.needs-knowledge` 플래그 + Stop 지식 저장소 게이트 — 지식 반영도 완료 조건으로 승격 |
| sync 누락 → 구버전 스킬이 설계 듀얼 리뷰를 조용히 생략, Claude 단독이 놓친 CRITICAL을 codex가 뒤늦게 적발 (2026-08-03 POK-30) | `.needs-dualreview` 기계 게이트 + Stop 차단 + Phase 0 정본 드리프트 확인 (다르면 작업 전 sync 먼저) |
| 게이트가 막을 때는 세 번 다 따랐는데, 게이트가 없는 축에서는 전부 혼자 정하고 보고서에 한 줄 적음 — 그 "한 줄"은 도구 호출이 아니라 문장이라 승인창도 안 뜬다 (2026-08-10 실측) | Stop 훅이 **대화 기록을 직접 읽는** 결정 게이트 — "자백은 있는데 질문이 0회"면 차단하고 걸린 문장을 보여준다. 게이트가 처음으로 산출물이 아니라 **행동**을 본다 ([ADR-0012](docs/decisions/2026-08-10-decision-gate.md)) |
| 검사기 자신이 어긋난 사본을 통과시킴 — 마커를 꾸미거나 블록을 2개 두면 무사통과 (2026-08-04 실측) | 전체 줄 3상태 파서 + 미등록 사본 스캔 + NUL 바이트 거부 게이트(UTF-16·NUL 위장으로 스캔을 통째로 비켜가던 경로) + 회귀 테스트 (건수의 정본은 테스트 파일의 `EXPECTED_CASES`) |

교훈의 패턴: **산문으로만 존재하는 절차는 언젠가 생략된다. 반복 실패는 훅·게이트·프로필로 승격하라.** (단, 선제 방어는 하지 않는다 — 실제로 겪은 뒤에 강제를 추가한다. YAGNI는 프로세스에도 적용된다.)

## 7. 알려진 한계 · 개선 후보 (자기 검토)

**정직한 한계 (구조적):**
- **게이트는 절차 강제이지 완전 강제가 아니다.** 플래그 삭제는 모델의 손에 있다 — 감사 없이 지우면 뚫린다. 방어는 3중: 지시(정의)·문화(게이트 무력화 금지 명문)·벽돌 방지 후에도 "완료 주장 신뢰 금지" 경고. 결정론적 바닥은 타입체크와 codex 호출 규율(PreToolUse 차단) 둘뿐.
- **스킬 자동 트리거는 세션 스냅샷 의존** — 설치 세션에는 발화하지 않음. 새 세션 1회로 확인 필요.
- **opus 전원 배치 + 검증 게이트마다 codex high는 비싸다** — 품질 우선의 의도된 선택(하향은 사용자 승인으로만). clarifier·change-explainer는 sonnet으로 낮춰도 손실이 작을 수 있는 후보(실사용 관찰 후 결정).

**개선 후보 (관찰되면 착수, 선제 금지 — YAGNI):**
