# ADR-0003: 스캔할 수 없는 대상은 검사 이전에 거부한다

**Date**: 2026-08-05
**Status**: accepted
**Deciders**: 김태윤(범위 판단), Claude(구현), codex(추가 경로 발견)

---

## Context

`scripts/check-rule-copies.sh`는 `template/` 아래에서 `rule:core` 토큰을 가진 파일을 찾아 정본과 대조한다. 그런데 스캔이 **원리적으로 못 보는** 대상이 있고, 전부 실측으로 `exit 0`이 재현됐다.

| 입력 | 왜 안 보이나 |
|---|---|
| NUL 1바이트 | `grep -I`가 바이너리로 판정해 파일을 통째로 건너뛴다 |
| UTF-16LE 저장 | `rule:core:start` 라는 **바이트열 자체가 없다** — `-a`로도 못 찾는다 |
| 심링크 | `grep -r`이 따라가지 않는데 `install.sh`의 `cp`는 실체를 풀어 배포한다 |
| 등록된 사본 블록 안 NUL | BSD awk가 NUL 이후를 버려 추출 결과가 정본과 같아지고 `cmp`가 통과한다 |

마지막 항목은 codex 리뷰가 찾았다. 앞의 셋과 경로가 완전히 다르다 — 등록된 파일이라 미등록 스캔의 대상조차 아니다.

## Decision

**스캔 불가 대상은 검사 이전에 거부한다.** 심링크 게이트와 NUL 게이트를 다른 모든 검사보다 앞에 두고, 하나라도 걸리면 즉시 `exit 1`.

판정식:
```bash
LC_ALL=C tr -d '\000' < "$f" | cmp -s - "$f"   # 비영이면 NUL 보유
```

근거 한 줄: **스캔할 수 없는 대상이 트리에 있으면 그 트리에 대한 스캔 결과 전체를 믿을 수 없다.**

## Alternatives Considered

### A. 인코딩별 패턴을 늘린다 (UTF-16LE 바이트열도 검색)
- **Pros**: 정당한 바이너리 파일을 막지 않는다
- **Cons**: 끝이 없다. UTF-16BE·UTF-32·BOM 변형마다 구멍이 다시 열린다. 방어가 공격보다 항상 한 발 늦는다
- **Why not**: 열거형 방어는 열거를 놓치는 순간 뚫린다. fail-closed로 뒤집는 편이 구조적으로 안전하다

### B. `grep -a`(바이너리도 텍스트 취급)만 쓴다
- **Pros**: 한 글자 수정
- **Cons**: NUL은 막지만 **UTF-16은 못 막는다** — `-a`는 바이너리 판정을 끌 뿐 인코딩을 변환하지 않는다(실측 확인)
- **Why not**: 반만 닫힌 방어. "고쳤다"는 착각을 남긴다

### C. 스캔에서 조용히 제외한다 (수정 전 `-I` 동작)
- **Cons**: 이게 발견된 결함이다. `-l`을 쓰면 `-I`가 지킬 대상이 애초에 없다(내용 출력을 이미 막음) — **이득 0에 fail-open 하나를 산 셈**. 실측: `-I` 있으면 2건, 없으면 3건
- **Why not**: 검사기의 존재 이유를 부정한다

## Consequences

### Positive
- **아직 발견되지 않은 변종까지 미리 막혔다.** UTF-16LE 대응으로 넣은 게이트가, 나중에 codex가 찾은 "등록된 사본 블록 안 NUL"(완전히 다른 경로)까지 함께 닫았다. 계층을 옳게 잡으면 이런 일이 생긴다
- 위양성 0 — `template/` 전 파일이 NUL 0바이트임을 확인
- 회귀 테스트가 게이트 제거 시 빨개지는 것까지 고정

### Negative
- `template/` 아래에 정당한 바이너리(이미지 등)를 둘 수 없다. `docs/usage.md`에 사용자 대면 제약으로 명시
- **원래 위협 모델("실수로 사본이 낡음")을 넘어선 적대적 방어다.** 김태윤이 이 점을 지적했고, 되감기 대신 마감을 택하되 PR #10 본문 "알려진 한계"에 그 사실을 공시했다
