# 2026-09-29 — 리뷰의 적용 단위: 계획 게이트는 개발 전 한 번, 무지적 3라운드는 PR 전체에서

## 결정 (kty 지시 「응 하네스 자체를 이렇게 바꿔 하네스 템플릿에도 이렇게 바꿔놓고」)

한 PR 을 여러 커밋으로 나눠 개발할 때 종결 규약을 커밋마다 되풀이하지 않는다.

1. **계획서는 개발 도중 커밋마다 코드에 맞춰 고치지 않는다.** 계획은 Phase 2 에서 한 번 리뷰받고 닫는다. 편차는 진행 기록과 통합 장부에 적고, 계획서와 운영 문서는 종결 라운드 전에 한 번 코드에 맞춘다. 커밋별 작업 지시·체크리스트를 쓰거나 고치는 일도 계획 게이트를 다시 열지 않는다. `[구조]` 부류 편차만 사용자에게 회부한다.
2. **커밋별 검수는 듀얼 1라운드다.** cc·cx 동시 1라운드(보안 트리거면 보안 검수 병렬) → CRITICAL/HIGH 만 고친다 → 수정분 확인 패스(cc·cx 동시) → 커밋. MEDIUM/LOW 는 이연해 PR 단계에서 처분한다.
3. **종결 = PR 전체 diff 를 입력으로 한 라운드에서 무지적 3회 ∧ 축 체크리스트 전부 커버.** 라운드 상한 5회는 종결 라운드에만 센다. 커밋별 라운드는 상한에도 무지적 계수에도 넣지 않는다.

듀얼 리뷰 구성(cc + codex 동시 · 모델·effort 고정 · 임의 하향 금지), 싱글턴 교차 검증, 라운드 보고, 변경 설명, 완료 감사, Phase 2 의 종결 조건(`[구조]` CRITICAL/HIGH 0), Phase 4 의 규약은 그대로다.

## 계기

pokeclip-mono 의 한 PR(커밋 9개 예정)이 착수 뒤 약 88시간이 지나도록 커밋 넷까지만 닫혔다. kty 가 「왤케 오래걸려? 뭐땜에 병목이생기는거야?」 · 「설계문제야?」라고 물었다. 기록 시각으로 어림하면 결정 대기가 약 28시간, 일한 시간이 약 60시간이고, 그 가운데 코드 개발·검수가 27시간, 계획 라운드가 20시간이었다.

원인은 둘이었다.

- **커밋마다 무지적 3회를 채웠다.** 종결 규약은 「코드 검수 게이트」에 무지적 3회를 요구할 뿐 적용 단위를 말하지 않는다. 같은 프로젝트의 앞 PR(커밋 7개)은 커밋마다 1라운드를 돌려 그 라운드를 무지적 계수에 넣고 PR 전체 diff 종결 라운드를 한 번 돌아 약 30시간에 닫았다. 다음 PR 은 같은 문장을 커밋마다 3회로 읽었다.
- **커밋이 끝날 때마다 계획서를 코드에 맞춰 고치고 그 계획서를 다시 듀얼 리뷰했다.** 계획서가 6,000줄을 넘겼고, 이 동기 라운드에 결정 대기가 걸려 있었다.

kty 의 말: 「그러니까 계획서 동기를 커밋마다 하는게 ㅈㄴ 쓸데없는 짓이라 이거지?」 · 「나도 전체적인 계획 짜놓고 리뷰 받은 다음에 마지막 pr 할 때 리뷰 ㅈㄴ 돌리는게 맞는것같은데?」

## 레퍼런스 조사

불요 — 리뷰의 구성(누가 · 어떤 모델로 · 무엇을 차단하는가)은 바꾸지 않고 같은 규약의 적용 단위만 정한다. 조직 밖 선례에 따라 달라질 결정이 아니고, 근거는 같은 프로젝트의 두 PR 실측이다. `2026-08-01-dual-review-rule.md` 의 「이 규칙을 개정할 때는 조사 대상이다」는 다중 모델 리뷰의 구성을 바꿀 때를 가리킨다.

## 치르는 값

- 커밋 단계에서 놓친 결함은 종결 라운드가 잡는다. 그때는 앞 커밋 위에 수정 커밋을 얹는다.
- 이연한 MEDIUM/LOW 가 PR 끝에 몰린다. 종결 라운드 전에 한꺼번에 처분한다.
- 커밋별 작업 지시의 `[구조]` 결함은 이제 계획 게이트가 아니라 그 커밋의 코드 검수에서 드러난다.
- 종결 라운드의 입력(PR 전체 diff)이 크다. codex 소모는 라운드당 늘고 라운드 수는 준다.
